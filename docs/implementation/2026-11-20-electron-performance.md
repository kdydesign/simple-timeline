# WorkRail 성능 개선 1·2차 구현과 검증

기준 커밋은 `3271e63`이다. 두 실험은 서로 다른 질문을 다룬다. 1차는 **간트와 달력의 인덱스 공유만** 적용한 빌드를 기존 빌드와 비교했다. 2차는 메인 프로세스의 저장·조회 및 릴리즈노트 창을 포함한 빌드를 비교했다. [구현 계획](../superpowers/plans/2026-11-20-electron-performance.md) · [1차 설계](../superpowers/specs/2026-11-20-home-planrail-performance-design.md) · [2차 분석](../harness/electron-phase2-2026-11-20.md)

## 1차 · Home 준비와 처음 일정을 선택하는 시간

App이 필터와 드래그 상태를 반영한 스냅샷의 인덱스를 만들고 간트·달력에 전달한다. 개별 뷰도 단독으로 열 수 있다. 후보 브랜치 `perf/home-planrail-index`의 회귀 검사에서는 필터 변경, 중복 이름, 가로 스크롤, 월 이동, 드래그 중 공유 회수를 확인했다. 같은 스냅샷에 대한 중복 생성은 별도 Electron 진단에서 확인했다. 1만 건의 서로 다른 스냅샷 두 개에서 인덱스는 총 4 → 2회 생성됐고, 그 한 쌍의 실행에서 생성 누적 시간은 31.2 → 22.6ms였다. [후보 브랜치의 인덱스 회귀 검사](https://github.com/kdydesign/simple-timeline/blob/perf/home-planrail-index/tests/ui/planrail-index.test.tsx)

각 크기에서 전후 24쌍, 총 96개 새 Linux Electron 프로세스를 교대로 실행했다. 첫 진입은 Home에서 PlanRail을 누른 뒤 화면에 보이는 일정 막대를 눌러 해당 편집기가 열린 시점까지다. 아래 값은 중앙값이며 단위는 ms다. [실험 조건과 재현 방법](../harness/evidence/home-planrail/README.md) · [96회 원시값](../harness/evidence/home-planrail/raw.json)

| 일정 수 | Home 준비 | 첫 PlanRail 진입·편집 | Home 왕복 후 다시 진입 |
| --- | ---: | ---: | ---: |
| 3건 | 520 → 510.5 | 50.6 → 54.3 | 30.3 → 36.2 |
| 1만 건 | 734 → 732.5 | 61.3 → 59.4 | 40.1 → 42.6 |

1만 건에서 Home 준비가 빨라진 쌍은 24개 중 11개였다. 스냅샷 응답부터 Home 준비까지는 중앙값 156.5 → 151ms였다. **중복 계산 제거는 확인했고, Home 시작 시간의 일관된 단축은 확인하지 못했다.** 메뉴 왕복도 빨라졌다는 근거가 없다. 승인 설계의 Home 지표 채택 기준이 충족되지 않아 1차 제품 변경은 독립 커밋과 `perf/home-planrail-index` 브랜치에 보관한다. `main`에는 2차 제품 코드를 반영한다.

## 2차 · 저장·조회와 릴리즈노트

- 일정 하나의 쓰기 권한은 해당 일정과 프로젝트의 공유 여부를 DB에서 확인한다. 로컬 알림 평가와 전체 무음 처리는 현재 역할에서 볼 수 있고 시작 또는 종료 알림이 켜진 일정만 읽는다. 공유 알림의 재승인, 전달 기록, 재시도 및 시각 판정 규칙은 기존 엔진이 담당한다. [로컬 알림 조회](../../src/main/db/repository.ts) · [알림 회귀 검사](../../tests/native/reminders.case.ts)
- 전체 일정 조회는 SQLite의 같은 읽기 트랜잭션 안에서 로컬 변경 수, 외부 커밋 버전, 스키마 버전을 확인한다. 세 값이 같은 경우 이전 스냅샷을 재사용하고 호출자에게 별도 DTO를 반환한다. 이미 진행 중인 트랜잭션의 읽기는 캐시에 게시하지 않는다. 새 쓰기 직후의 최초 조회에는 여전히 DB 읽기가 필요하고, 캐시도 메인 힙을 사용한다. [공유 저장소](../../src/main/sharing/repository.ts) · [롤백·다른 연결의 커밋·공유 권한 회수 검사](../../tests/native/sharing-snapshot.case.ts)
- 사용자가 선택한 창 정책에 따라 릴리즈노트 ×는 창을 해제한다. 앱 실행 중 메인이 버전·스크롤과 창 위치를 기억한다. 읽던 창의 마지막 스크롤을 확인할 수 없는 경우 마지막으로 확인한 위치를 사용한다. 주 창을 트레이로 숨길 때는 열려 있던 보조 창을 함께 숨겨 복원한다. 도움말의 사전 준비와 재사용은 유지한다. [릴리즈노트 창 수명주기](../../src/main/release-window.ts) · [실제 Electron 검사](../../tests/e2e/release-notes.spec.ts)

### 데이터가 바뀌지 않았을 때의 재조회와 보조 창 비용

양쪽 빌드에서 독립 프로필 3개씩 측정했다. 데이터 1만 건의 반환을 실행마다 20번 요청했다. 아래 시간은 실행별 통계의 중앙값이다. PSS는 Linux에서 공유 페이지 비용을 프로세스별로 나눠 합한 메모리다.

| 관찰 지표 | 기존 | 변경 후 |
| --- | ---: | ---: |
| 전체 일정 조회 IPC 왕복 | 61.4ms | 45.0ms |
| 비교용 저장소 상태 조회 IPC 왕복 | 0.6ms | 0.6ms |
| 전체 조회 중 메인 5ms 타이머의 실제 간격 p95 | 30.1ms | 16.1ms |
| 전체 조회 중 메인 타이머의 최대 간격 | 148.1ms | 109.0ms |
| 도움말만 열었다가 닫은 시점의 앱 PSS | 280.0MiB | 280.3MiB |
| 릴리즈노트도 한 번 열고 닫은 뒤 앱 PSS | 316.8MiB | 284.7MiB |
| 도움말만 있던 시점 대비 같은 실행의 PSS 증가분 | 36.8MiB | 4.1MiB |
| 릴리즈노트 재열기 요청부터 제목 준비와 두 프레임 경과까지 | 28.5ms | 124.6ms |

릴리즈노트를 닫은 뒤 해당 renderer의 PSS는 35.2MiB에서 0으로 바뀌었고, 도움말 renderer는 같은 PID로 유지됐다. 다시 연 창은 선택했던 버전을 복원했다. 메인 타이머 간격이 50ms를 넘은 횟수는 조회 20회당 중앙값 3회로 양쪽이 같았다. 반복 조회 비용이 줄어도 긴 지연이 발생할 수 있다.

### 일정 1만 건에서 한 건 수정

일회성 프로필에서 간트의 일정 하나를 편집하고 확인창의 변경 버튼을 눌렀다. 다음 값은 양쪽 빌드별 5회 중앙값이다. 함수 구간은 실험용 번들에서 계측했다. 창 제어는 같은 저장을 별도 5회 실행해 재조회 중 최대화 명령의 응답을 측정했다. Xvfb에서는 실제 최대화 상태가 바뀌지 않아 물리적인 창 전환 시간은 측정할 수 없었다. [원시값·측정한 소스 패치·재현 스크립트](../harness/evidence/save-release-benchmark.zip)

| 구간 | 기존 | 변경 후 |
| --- | ---: | ---: |
| 저장부터 첫 새로고침까지의 로컬 전체 일정 조회 | 3회 | 1회 |
| 쓰기 권한 평가 | 13.4ms | 0.05ms |
| 로컬 알림 대상 조회 | 14.0ms | 0.99ms |
| 저장 IPC 왕복 | 47.7ms | 27.8ms |
| 쓰기 후 첫 전체 조회 IPC 왕복 | 67.7ms | 78.6ms |
| 변경 확인부터 새 이름이 간트에 표시될 때까지 | 168.2ms | 152.7ms |
| 변경 확인부터 화면 반영 후 두 프레임까지 | 175.9ms | 170.0ms |
| 이 구간과 겹친 메인 5ms 타이머의 최대 간격 | 51.1ms | 152.3ms |
| 재조회와 겹친 창 명령 IPC 왕복 | 70.8ms | 98.9ms |

쓰기 후 첫 조회에서는 캐시를 다시 채워야 한다. 그 조회의 메인 dispatch는 26.7 → 31.4ms, IPC 왕복 중 dispatch 바깥은 37.1 → 50.2ms였다. 데이터가 바뀌지 않은 반복 조회와 결과가 다르다. 변경 후 화면 반영까지 두 프레임이 681.7ms 걸린 한 건도 위 집계에 포함했다. 타이머 간격에는 OS 스케줄링이 포함되고, 시작 또는 끝이 UI 관찰 구간을 넘어갈 수 있다.

### 제품 빌드에서 단건 저장 재확인

함수 계측을 뺀 Linux 제품용 Vite 엔트리에서 같은 1만 건 DB의 복사본으로 별도 실험했다. 각 빌드·조작에서 5회씩 실행했다. 저장 중에는 DOM이 데이터를 반영하는 시점과 메인 타이머·스레드 CPU만 관측했다. 조회 결과의 첫 복사를 생략하는 실험 빌드까지 합해 새 프로세스 30개를 사용했다. 측정 시점과 구성이 앞선 번들 실험과 달라 두 표를 합산하지 않는다. [제품 빌드 원시값·비교 패치·재현 방법](../harness/evidence/clean-production-save.zip)

| 중앙값 | 기존 | 통합 빌드 |
| --- | ---: | ---: |
| 저장 확인 클릭 → 새 이름이 간트에 표시 | 162.6ms | 148.8ms |
| 저장 확인 클릭 → 화면 반영 후 두 프레임 | 165.8ms | 151.9ms |
| 단건 저장 중 메인 타이머 최대 간격 | 49.1ms | 33.6ms |
| 위 최대 간격 안에서 메인 스레드가 사용한 CPU | 41.3ms | 32.2ms |
| 저장 중 전송한 최대화 명령 응답 | 60.4ms | 68.3ms |

통합 빌드 단건 저장의 타이머 최대 간격은 29.4~65.2ms였다. 앞선 실험에서 나타난 130ms 이상의 간격은 이 다섯 번에서는 재현되지 않았다. 차이를 만든 원인은 확정할 수 없다. 저장 중 창 명령 응답은 양쪽 범위가 겹쳤고, 빨라졌다는 근거가 없다. 호출자별 DTO 복사를 일부 생략하는 실험도 비교했으나 일관된 이점이 없어 기존 호출자 격리를 유지했다.

## 검증 환경과 인수 범위

- Linux x64, Node 24.22.1, Electron 45.2.1, Xvfb와 Chromium sandbox를 사용했다. 실제 사용자 프로필은 사용하지 않았다. 로컬 전체 검사 보고서는 기준 HEAD `3271e63` 위의 구현 변경을 포함한 dirty 트리에서 생성됐다.
- `npm run verify:app`의 7단계가 통과했다. 3개 시간대에서 각각 단위 테스트 702건 통과·플랫폼 조건 8건 건너뜀, UI 349건, 네이티브 103건, 실제 Electron E2E 128건 통과다. E2E 재시도 통과와 건너뜀은 각각 0건이다. 숨긴 창과 명시적으로 닫은 창의 구분, 전용 ×와 네이티브 닫기 후 읽기 위치 복원, 편집 초안 및 메뉴 왕복 스크롤을 확인했다.
- 2차 단독 소스 `519ee7a`의 첫 전체 검사는 E2E 127건 통과·1건 실패였다. TermRail 별도 창에서 `pagehide` 직후 한 번만 읽은 `Window.closed`가 아직 false였다. 창 닫힘 조건을 관찰하도록 해당 테스트를 보정했다. 개별 5회 연속 통과 후 2차 단독 전체 검사를 다시 실행해 7단계와 E2E 128건이 통과했다. 마지막 보고서의 HEAD는 `519ee7a`, dirty는 true이며 수정된 항목은 테스트와 임시 의존성 링크였다.
- Windows GitHub 호스팅 VM의 기존 설치·업데이트 시나리오에 150% Chromium 배율에서 Home 시작 → PlanRail → 기존 일정 편집을 확인하는 단계를 넣었다. 실행 결과의 `homeToPlanrailEditorScale` 필드에 renderer에서 확인한 배율을 기록한다. 같은 기기에서 3건·1만 건의 설치본을 전후 반복 측정한 Windows 수치와, 사용자 PC의 디스플레이·GPU·백신 영향은 별도 확인 대상이다. [설치본 검증 코드](../../tests/e2e/packaged.spec.ts)
