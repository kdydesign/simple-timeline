# WorkRail 1.0.0 — 구현·검증 기록

상태: 로컬 구현·최종 보완·독립 검토·전체 자동 검증 완료. 게시·원격 CI·Windows 실기 완료 기록이 아니다.
기준 소스: Planrail 0.8.8 `05e972da7282046f2fd2bee584c9ceee7beba007`.
사용자는 [설계](../design/team-tool-expansion.md)의 WorkRail 이름, 하단 도크 D, Node 목록 A, 통합 현황 홈 B, W 레일 아이콘 A를 선택하고 구현을 요청했다.
[구현 계획](../superpowers/plans/2026-11-18-workrail.md)에 따라 진행한다.

## 구현 경계

- 사용자에게 보이는 상위 앱 이름은 WorkRail, 일정 도구 이름은 Planrail이다.
- 기존 `com.kdydesign.simpletimeline`, `SimpleTimeline` 프로필, `Planrail.exe`, LAN 업데이트 파일 형식·서명 정책·승인 정보는 보존한다. 내부 실행 파일과 산출물 이름 일부에는 Planrail이 남는다. 고정된 builder의 실제 AppInfo 계산상 기본 설치 폴더도 Planrail이며 표시 이름·바로가기는 WorkRail이다.
- 새 앱 버전은 1.0.0으로 준비했다. 이는 이번 주요 제품 전환에 대한 구현 판단이며 아직 배포하지 않았다.
- 선택한 W 심벌은 작은 크기에 맞춘 SVG 원본과 PNG, 16/24/32/48/64/256 ICO로 제작했다. 비교 이미지와 생성 원본은 채팅 작업공간에 보존했다.
- Node 관리는 Windows x64와 공식 nvm-windows 1.2.2를 대상으로 한다. 최초 설치 지원은 공식 1.2.2 설치 파일의 고정 SHA-256을 확인한다. 다른 버전은 감지·안내하고 덮어쓰지 않는다.

## 작업공간과 검증 환경

원래 `/workspace/simple-timeline`의 협의 변경은 보존하고, 최신 main을 기준으로 `/workspace/workrail`의 `workrail` 브랜치를 생성했다. 사용자 지시에 따라 원격 push·환경 게시를 하지 않는다.

Linux x64, Node 24.22.1, Electron 45.2.1. `npm ci`는 Electron 헤더 다운로드가 프록시403으로 막혀 postinstall 재빌드에서 실패했다. 설치된 better-sqlite3 13.0.3의 번들 NAPI 바이너리가 Electron에서 실제 메모리 DB 생성·조회·닫기를 통과했으며, 소스의 설치 절차나 의존성 버전을 우회 변경하지 않았다. 최종 native 검사는 별도 실행 결과로 기록한다.

Xvfb가 없는 환경이므로 dummy 드라이버의 별도 Xorg `:121`과 xfwm4를 사용한다. Electron sandbox는 유지한다. 테스트는 격리 프로필만 사용하며 실제 nvm 설치·버전 전환을 자동 실행하지 않는다.

## Windows에서 별도로 확인할 범위

Linux의 가짜 Windows 어댑터 검사와 실제 Windows UAC·nvm 동작은 구분한다. 격리된 Windows PC에서 기존0.8.8 설치본→WorkRail 업데이트 후 일정·승인 PC·설정 보존, nvm 미설치/공식1.2.2/비호환 버전, 관리자 승인·취소, Node 설치·전환 후 PowerShell/CMD/VS Code의 후속 node 실행, standalone Node/PATH 충돌 및 복구를 확인해야 한다. 실행 중인 기존 Node 프로세스를 바꾸는 기능은 없다.

## Node 연동의 명시적 제한

공식 설치 파일의 내려받기는 Node fetch로 수동 redirect를 검증한다. 이 경로는 Windows 시스템 프록시를 자동 발견하지 않는다. 프록시 환경에서 다운로드가 실패하면 공식 릴리스의 nvm-windows1.2.2를 수동 설치한 뒤 환경을 다시 확인할 수 있다. Node 목록은 별도 Electron 통신 경로다.

권한 브리지 종료로 실제 승격 작업의 완료를 알 수 없는 경우 파일 존재만으로 성공이나 작업 종료를 판단하지 않는다. 오류와 보호 상태를 유지해 추가 Node 변경·앱 종료·업데이트를 차단하며, 열린 설치/권한 창과 실제 프로세스를 확인한 뒤 복구해야 한다. 정상 완료·취소와 이 불명 상태를 구분한다.

## 최종 검토 보완

전체 변경 검토는 Windows 권한 작업의 PowerShell·작업 폴더·PATH·ComSpec를 상속된 SystemRoot에서 결정하는 문제1건과 오류 진단·옛 표시 이름2건을 지적했다. `f3b3493c8d8b9f081ba30f940e75254008601e83`은 Windows의 운영체제 네임스페이스에서 시스템 폴더의 실제 경로를 확인하고, 경로·파일 식별 정보와 작업자의 시스템 경로가 맞지 않으면 프로세스 실행을 차단한다. 원래 nvm·설정·설치 파일 검증과 종료 불명 보호는 유지한다.

환경 변수 조작·해석 실패·경로 불일치 및 복구 진단을 실패로 재현한 뒤 집중 Node·도움말 단위50개, UI19개, 네 타입 검사와 일반 빌드를 통과했다. 수정 재검토는 새 Critical·Important가 없음을 확인했으며 전체 검증도 아래와 같이 통과했다. 네이티브 경로 조회와 Windows UAC의 실제 실행은 여전히 Windows 실기 검증 대상이다.
