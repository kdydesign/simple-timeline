선택한 방식은 기존 API와 DTO를 유지하는 내부 계산·조회 최적화다. 페이지 단위 IPC나 별도 DB 프로세스는
실패·상태 계약을 확대하므로 채택하지 않았다. 모든 SQL을 일괄 재작성하기보다 측정된 반복 조회를 줄였다.

## 반영

- snapshot은 한 읽기 트랜잭션 안에서 참여자·프로젝트·일정 세 번만 조회한다.
  참여자는 project_id/position 순서로 묶으며 빈 참여자·큰 수치 ID·프로젝트/일정 정렬을 유지한다.
  SQL statement만 재사용하고 데이터 결과는 매번 새로 읽는다. DTO 변환은 전달된 참여자를 사용한다.
- [주별 집계](../../src/visualization/calendar.ts)의 hiddenCountsForWeek는 칸별 Set으로 동일 ID 중복을 제거한다.
  한 주의 배치 조각을 입력받고 월 밖/지원 연도 밖 칸의 비활성 처리는 기존 화면 계약을 따른다.
  기존 단일 날짜 hiddenCount는 호환과 비교 회귀에 남겼으며 화면의 반복 호출에서 제외했다.
- 선택 날짜의 전체 목록은 snapshot/day가 바뀌면 다시 계산한다. 저장·삭제 뒤 새 snapshot을 반영한다.

## 보정·검증

실제 SQLite verbose 로그 기반 회귀를 먼저 실행해 프로젝트 200개에서 SELECT 202회를 확인했다.
3회 이하 조건이 실패한 뒤 구현을 바꿔 통과했다. 참여자 순서·빈 프로젝트·수정 후 재조회도 검사한다.
주별 함수가 없던 상태의 신규 검사는 실패했고, 구현 후 일곱 칸의 수·중복 ID·빈 주 검사를 통과했다.

동일 Linux x64·Node 24.22.1에서 1만 개 일정이 한 주 전체에 겹치는 입력으로 결과 일치를 확인했다.
5회 예열, 15회 실행 중앙값: 기존 날짜별 집계 **89.23ms**, 주별 집계 **6.83ms** (약 13배).
이는 집계 함수만의 관측이며 전체 앱 지연·Windows PC·임의 데이터 규모의 성능 보장이 아니다.
새 방식은 계산 중 일곱 Set을 사용하며, memo에 보존하는 값은 주당 일곱 개 숫자다.

## 독립 코드 검토

Superpowers requesting-code-review 절차의 읽기 전용 검토에서 수정이 필요한 결함은 발견되지 않았다.
statement 생성 시점·같은 연결/트랜잭션, 참여자/큰 ID/정렬, memo 갱신, 월 경계와 9999년 끝의 열 대응을 확인했다.
잘못된 열/span이나 여러 주를 섞은 입력은 단일 주 배치 함수의 내부 계약 밖이다. 현재 호출자는
calendarSegments/placeWeek의 유효한 한 주만 전달하므로 별도 입력 API·검증 정책을 추가하지 않았다.
