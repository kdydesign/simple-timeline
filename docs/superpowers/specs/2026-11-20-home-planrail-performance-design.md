# Home 준비와 첫 PlanRail 진입 성능 개선 설계

2026-11-20 · 우선순위와 1차 접근 선택 완료 · 설계 승인 대기

사용자는 Home과 첫 PlanRail 진입을 함께 개선 대상으로 선택했다. 1차 실험은 현재 보이는 일정 목록의 정렬·분류 결과를 간트와 달력이 공유하는 것이다. 사용자에게 중요한 두 시점은 **앱을 켜고 Home의 일정을 볼 수 있을 때**와 **PlanRail을 처음 눌러 실제 일정을 선택할 수 있을 때**다.

## 근거와 대안

일정 3건과 1만 건의 Linux 재시작 실험에서 창 표시 중앙값은 각각 246ms·254ms, Home 데이터 준비는 472ms·619ms였다. 1만 건 트레이스 한 건에서 인덱스 생성 포함 시간은 간트 13.1ms, 달력 10.4ms였다. 147ms는 데이터 규모에 따른 전체 준비 시간의 차이다. 인덱스 공유로 절감할 시간은 실험으로 결정한다. 첫 PlanRail 진입 시간은 기존 보고서에 기준값이 없어 변경 전에 먼저 측정한다. ## 데이터 흐름과 기능 계약

- 두 뷰의 공통 부모에서 현재 표시용 스냅샷인 `visibleSnapshot`을 입력으로 기존 `indexSnapshot` 결과를 한 번 계산한다. 동일 참조의 스냅샷을 사용하는 동안 간트와 달력은 같은 결과를 읽는다. 입력이 없으면 인덱스도 생성하지 않는다. 개별 뷰를 직접 마운트하는 기존 호출 경로도 지원한다. [공통 부모](../../../src/renderer/App.tsx) · [정렬·이름 구분 규칙](../../../src/visualization/presentation.ts)
- 표시용 스냅샷에는 전체·개인·공유 필터와 드래그 중 고정된 데이터가 반영돼 있다. 원본 DB 스냅샷을 키로 삼으면 필터 또는 권한 회수가 늦게 반영될 수 있다. 표시용 입력이 바뀌면 두 뷰가 새 인덱스를 함께 사용한다. 프로젝트별 일정 배열과 이름 맵은 읽기 전용으로 취급한다. [공유 필터와 드래그 동작](../../../src/renderer/state/useSharingView.ts)
- 메뉴 왕복 후 스크롤·선택일·편집 초안이 복원되는지, 같은 이름의 일정 구분과 정렬 순서가 일치하는지, 공유 일정이 드래그 중 회수되면 두 뷰에서 사라지는지 검사한다. 가로 스크롤·날짜 이동만으로 전체 인덱스가 다시 생성되는지도 검사한다.
- 1차 변경 대상은 renderer의 인덱스 생성과 전달이다. SQLite 전체 조회·IPC 전달 방식, 알림 평가 주기, 기존 메뉴의 마운트 정책은 각각 독립적으로 효과를 측정할 후속 후보로 둔다.

## 실험과 채택 기준

1. 변경 전후 동일한 Electron 빌드 조건·일회성 프로필·창 크기에서 일정 3건과 1만 건을 각각 측정한다. fixture 삽입은 측정 전에 마친다. 각 조건 최소 5회, 전후 실행 순서를 번갈아 하며 중앙값·범위·원시값을 보존한다. 기존 보고서의 Home 준비 마크와 동일한 시계를 사용한다.
2. 첫 PlanRail 진입은 Home 준비 후 메뉴 클릭부터 첫 표시 일정 막대를 실제로 선택하고 해당 일정 편집기가 열릴 때까지 측정한다. 기준 일정이 처음부터 뷰포트 안에 있도록 양쪽 프로필의 시작일·선택 월을 고정한다. 메뉴 왕복은 별도 측정해 첫 진입 결과와 분리한다.
3. 무계측 실행에서 두 사용자 지표를 비교한다. 별도 프로파일에서 같은 표시 스냅샷에 대한 중복 생성 제거를 확인한다. 1만 건에서 Home 준비 시간 개선이 반복되고, 첫 PlanRail 진입 및 3건의 두 지표가 기준선의 반복 편차 안에 있으며 기능 회귀가 없으면 채택한다. 차이가 편차와 구분되지 않으면 양쪽 반복 수를 늘려 판단을 보류하거나 채택 근거를 보강한다.
4. Windows 설치본에서도 같은 사용자 경로를 150% 배율로 확인한다. OS·기기·GPU·보안 프로그램 조건은 측정 기록에 남긴다. Linux 결과와 Windows 결과를 각각 보고하고, PostRail 도입 전후 비교는 별도 대조 실험으로 다룬다.
