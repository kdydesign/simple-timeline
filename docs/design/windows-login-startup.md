# Windows 로그인 자동 실행 — 0.8.1

2026-11-12. Q1~Q9 협의 및 제한된 강제 종료 제안을 포함해 사용자가 전체 구현을 승인했다. 구현·검증 상태는 후속 실행 기록을 따른다. 삭제 버튼·UPDATE 스타일은 별도 승인 범위다.

## 목적과 범위

현재 Windows 사용자가 로그인하면 Planrail을 트레이에서 실행해 기존 공유·동기화·알림을 이용한다. 로그인 전 실행, Windows 서비스, 강제 절전 방지, 관리자 권한 설치는 추가하지 않는다. 공유 시작·중지의 마지막 선택과 기존 개인·호스트·멤버 동작은 유지한다.

## 합의한 동작

| 항목 | 결정 |
| --- | --- |
| Q1 설치 선택 | ‘Windows 로그인 시 Planrail 자동 실행’ 체크박스. 처음 선택할 때 기본 체크. 현재 사용자에게만 적용 |
| Q2 실행 방식 | 로그인 자동 실행은 창을 띄우지 않고 트레이로 시작. 직접 실행·바로가기·Open은 창을 표시 |
| Q3 설치 후 변경 | 트레이에 체크 가능한 ‘Windows 시작 시 자동 실행’ 항목으로 현재 상태 확인·변경 |
| Q4 업데이트 | 대화형 설치는 이전 선택을 표시. 무인 UPDATE는 기존 상태 보존. 설정이 없던0.8.0 PC에도 임의로 켜지 않음 |
| Q5 예외 표시 | 트레이 생성 실패·DB 오류 등 조치가 필요한 시작 문제는 창 표시. 일시적인 공유 연결 끊김은 트레이 유지 |
| Q6 OS와 메뉴 | Windows에서 사용 중지한 상태를 존중. 앱에서 사용자가 다시 켤 때만 활성화. 아래 순서 적용 |

```text

✓ Windows 시작 시 자동 실행
────────

```

설치 완료의 ‘지금 실행’은 이번 한 번 실행하는 선택이며 로그인 자동 실행과 별개다. 자동 업데이트 후 재실행 동작은 기존과 같다. 트레이 Exit는 현재 실행을 종료하며 자동 실행 설정을 끄지는 않는다.

## 구현 접근과 수명 관리

현재 사용자 Run 등록을 설치 프로그램과 앱이 동일한 이름·실행 경로·전용 자동 실행 인자로 관리한다. 등록된 경우에도 Windows의 시작 앱 사용 중지 상태를 확인한다. 일반 실행에서 등록을 자동 복구하거나 다시 활성화하지 않는다. 개발 실행은 사용자 시작 앱에 개발용 Electron을 등록하지 않는다.

기존 NSIS 디렉터리 선택 뒤 별도 옵션 페이지를 사용해 완료 화면의 즉시 실행과 구분한다. 무인 업데이트에서는 체크박스 기본값을 적용하지 않는다. 업데이트 중 기존 설치 제거 단계는 등록을 보존하고, 실제 앱 제거는 이 앱의 자동 실행 등록만 정리한다. 기존 DB 보존 정책은 유지한다. 앱에서 설정 변경에 실패하면 성공으로 표시하지 않고 오류와 실제 상태를 안내한다.

Windows 시작 폴더 바로가기와 서비스 방식도 가능하지만, 서비스는 로그인 전 실행·권한 범위가 요구보다 크다. 이 설계는 현재 사용자 등록 방식으로 구현하고 별도 상주 서비스나 외부 도구를 추가하지 않는다.

## 검증 기준

- 새 대화형 설치 기본 체크, 해제 설치, 기존 ON/OFF 재설치 선택 보존.
- 0.8.0→0.8.1 무인 업데이트에서 기존 미등록 유지; 이후 ON/OFF 업데이트 보존.
- 실제 Windows 로그인 자동 실행 시 창 깜빡임 없이 트레이 표시, Open·바로가기·두 번째 실행은 기존 창 표시.
- 트레이 실패·DB 오류 시 창 표시, 공유 연결 오류는 숨김 유지.
- 트레이 ON/OFF 변경·실패 안내, Windows 작업 관리자에서 사용 중지한 상태 존중.
- 업데이트 중 제거와 실제 제거 구분; 사용자 지정 경로·공백 포함 경로·기존 DB 보존.

자동 검증·Windows CI·실제 사용자 로그인 검증을 구분해서 기록한다. 설치 테스트는 기존 프로필이 없는 일회성 Windows VM에서 수행한다.

## 추가 협의: 실행 중 수동 설치

Q7에서 사용자는 다운로드한 설치 EXE를 직접 실행했을 때 기존 앱 종료 안내 후 설치 중단을 확인했다. 현재 `customCheckAppRunning`은 종료를 요청하지 않고 최대30초 대기 후 중단한다.

Q8의 사용자 요청은 확인 없이 작업을 폐기하고 설치를 우선하는 것이다. 미저장 입력을 버리고 설치를 계속하는 방향이며, 기존에 제안한 ‘변경 버리기 확인’은 채택하지 않았다. 기술적으로는 새 입력·쓰기를 막고 이미 시작된 DB 쓰기를 완료 또는 안전하게 취소한 뒤 서비스·DB·앱을 종료해야 한다. 이미 commit된 데이터는 삭제하지 않는다. 이 수동 설치 정책을 기존 앱 내 UPDATE의 미저장 입력 보호에 자동 확대하지 않는다.

실행 중0.8.0은 외부 종료 요청을 받는 기능이 없다. `second-instance`는 창만 표시하고 일반 창 닫기는 트레이로 숨긴다. 앱과 설치본 양쪽에 종료 요청 처리를 추가해야 한다. Q9 검토 후 사용자는0.8.0의 제한된 강제 종료를 포함한 전체 설계 구현을 승인했다.

### Q9 검토 결과와 제한된 강제 종료 제안

사용자는0.8.0 강제 종료 방식 검토 후 아래 제한과 영향을 안내받고 전체 구현을 승인했다.

현재 DB는 `journal_mode=DELETE`, `synchronous=FULL`을 사용한다. `db/lifecycle.ts`는 hot rollback journal이 있으면 DB·journal 원본을 보존하고 SQLite 복구를 수행한다. 기존 `tests/native/lifecycle.case.ts`에는 프로세스 강제 중단 후 commit된 데이터 및 복구 원본 보존 검사가 있다. 강제 종료가 항상 DB 손상을 일으킨다고 단정하지 않으며, 이 검사도 실제 회사 PC의 모든 파일 시스템·보안 프로그램 동작을 보장하지는 않는다.

미저장 입력은 유실된다. 종료 직전 이미 commit된 저장은 남을 수 있어 진행 중인 저장의 일괄 폐기를 보장할 수 없다. DB 외 공유 자격 파일·페어링·설정 기록은 다른 저장 단계가 있고, 알림 전송 도중 중단되면 결과 불명으로 남아 중복 방지 정책에 따라 자동 재전송하지 않을 수 있다.

승인된 적용 범위:

- 사용자가 설치 EXE에서 설치를 시작한 대화형 수동 설치에만 적용한다. 앱 내 UPDATE와 일반 무인 설치에는 강제 종료를 추가하지 않는다.
- 현재 사용자·정확히 같은 설치 EXE 경로·확인 가능한 설치 버전0.8.0의 프로세스만 대상으로 한다. 실행 파일명만으로 일괄 종료하지 않는다. 대상 신원 확인이나 종료가 실패하면 설치 파일을 교체하지 않는다.
- 대상 종료를 확인한 뒤 설치를 계속하고 기존 DB·journal·사용자 데이터를 삭제하지 않는다. 추가 미저장 확인은 하지 않는다.
- 0.8.1 이상은 새 정상 종료 요청으로 미저장 입력을 버리고 수락한 DB 작업을 마무리한 뒤 설치한다. 정상 종료 실패를 강제 종료로 자동 전환하지 않는다.
- Windows CI의 일회성 프로필에서 실제0.8.0 실행 중 설치·미저장 입력 소실·commit된 데이터 보존·다른 경로 프로세스 비종료·권한 실패 시 중단을 검증한다. 사용자 회사 PC 실기는 별도다.
