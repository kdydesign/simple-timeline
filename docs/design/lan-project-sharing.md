# 사내 대표 PC를 통한 프로젝트 공유·동기화

작성: 2026-11-10. 상태: **Q1~Q24 확정. 전체 설계 최종 검토 대기. 제품 구현 미착수.**
기준 코드: `50838365e393b6f95ee5710b41a9d6c24a0e4828` (Planrail 0.5.0).
Superpowers와 grill-with-docs의 grilling·domain-modeling을 적용한다.
기존 MVP 완료 상태를 유지하며 이번 작업은 후속 기능 설계다.

## 목적

A·B·C가 각 PC에 Planrail을 설치하고 같은 공유 프로젝트를 사용한다.
호스트가 공유 일정을 추가·수정·삭제하면 등록된 멤버의 앱에도 반영한다.
멤버는 공유 자료를 조회하고 자신의 알림을 설정하며, 개인 프로젝트는 계속 자유롭게 관리한다.

## 이미 확정된 방향과 확인 결과

- 외부 서버·외부 클라우드에 일정 데이터를 저장하지 않는다. 회사 내부에서 사용한다.
- 별도 서버 장비 대신 대표 PC A를 공유 호스트로 사용하고 B·C가 사내망으로 연결한다.
- 사용자 보고: A에서 Python 임시 HTTP 서버를 띄우고 B·C가 A의 IPv4 주소, 포트 8765의 test.txt에 접속해 테스트 문자열을 확인했다.
- 이 결과는 당시 PC·포트의 HTTP 연결 확인이다. 제품 동기화·인증·암호화·장기 연결·재연결 성공까지 검증한 것은 아니다.
- Python 서버·8765 포트를 제품 구성으로 확정한 것은 아니다.

## 현재 구현에서 확인한 사실

| 항목 | 사실과 근거 |
| --- | --- |
| 참여자 | [용어](../../CONTEXT.md)와 [타입](../../src/shared/types.ts): 표시용 이름 목록이며 계정·권한·담당자가 아님 |
| 저장 | [저장 설계](storage.md), [스키마](../../src/main/db/schema.ts): 사용자별 로컬 SQLite, 테이블별 AUTOINCREMENT ID. 여러 PC의 ID를 그대로 섞으면 충돌할 수 있음 |
| 수정 | [저장소](../../src/main/db/repository.ts): ID 기반 수정, 공동 편집을 위한 revision 비교 계약 없음 |
| 통신 | [API](../../src/shared/api.ts), [IPC 검증](../../src/main/ipc-core.ts): 신뢰한 로컬 renderer와 main의 제한된 IPC. 원격 사용자 인증을 대체하지 않음 |
| 날짜 | 기존 YYYY-MM-DD, 0001~9999, 양 끝 포함 규칙은 유지 대상 |

추가 조사:

- 현재 변경 요청에는 재전송 중복 방지용 작업 ID가 없으며, 삭제는 실제 DELETE다. 증분 수신을 위한 변경 순번·삭제 기록도 없다.
- renderer의 `connect-src 'self'`와 제한된 preload는 유지할 보안 경계다. main 자체가 모든 네트워크를 차단하는 구조는 아니다.
- [알림 설정](../../src/domain/reminder.ts)은 일정에 포함되고 전송 이력은 로컬 DB에 있다. 이를 그대로 공유하면 수신자별 설정·중복 억제 의미가 달라진다.
- [현재 종료 동작](../../src/main/close.ts)은 트레이 숨김·완전 종료·취소를 선택하며, 종료 보호는 로컬 renderer의 저장 상태를 확인한다. 원격 요청 처리 중 종료는 새 계약이 필요하다.
- 기존 Windows 오프라인 CI는 outbound 전체 차단 하에 개인 CRUD를 확인한다. 인터넷 차단과 LAN 연결 허용은 검증 조건을 분리해야 한다.
- 설정·공유 연결·접속 사용자 UI는 아직 없다. 로그인 자동 실행이나 별도 Windows 서비스는 대표 PC 방식 선택에 자동 포함하지 않는다.
- 문서 불일치: 배포 정책의 ‘창 X는 숨김’은 0.5.0 이전 설명이다. 이번 설계의 현재 동작 근거는 최신 코드와 사용 안내의 매번 선택 방식이다.

## 설계안의 지위와 접근 대안

Q1~Q24는 사용자 확정 사항이다. 아래에서 해당 질문으로 명시한 운영 정책도 확정되었다.
구체적인 통신·저장·화면 계약은 이를 실현하기 위한 **작성자 기술 제안이며 전체 설계 승인 전**이다.
제품 구현·의존성 추가·운영 정책 적용은 하지 않는다. 현재 코드의 구조를 구현 완료된 공유 구조로 설명하지 않는다.

| 비교한 접근 | 선택과 이유 |
| --- | --- |
| 외부 서버 / 사내 대표 PC | 외부 서버를 둘 수 없다는 사용자 제약에 따라 대표 PC를 선택. 전용 서버 장비 없이 시작할 수 있으나 호스트 실행·네트워크 상태에 의존 |
| 멤버 편집 허용 / 호스트만 편집 | Q16에서 호스트만 CRUD로 확정. 멤버 원격 쓰기·공동 편집 충돌·오프라인 쓰기 큐는 제공하지 않음 |
| 호스트 즉시 전달 / 2초 변경 확인 | Q19에서 후자를 선택. 연결·재연결 복구를 단순하게 유지하고 정상 LAN 5초 이내 반영을 검증 |
| 개인 원본 복사 / 원본 공유 전환 | Q10·Q20에서 원본 전환 선택. 별개 개인 복사본을 남기지 않으며 실패 시 기존 자료 유지 |
| IP만 확인 / IP와 승인 자격 확인 | Q7·Q17에서 후자와 암호화 선택. 주소 재할당만으로 다른 설치본에 권한이 생기지 않도록 함 |

SQLite 파일을 네트워크 폴더에서 여러 PC가 직접 여는 방식은 채택하지 않는다. 호스트 main만 기준 DB에 접근하고 멤버는 제한된 조회 응답을 받는다.

## 구성과 권한 경계

- 호스트: 기존 로컬 DB의 프로젝트에 개인/공유 구분을 추가한다. 공유 원본·참여자·승인 설치본을 소유하며 기존 로컬 저장 경로로만 CRUD한다.
- 멤버: 개인 자료와 별도로 공유 수신 캐시를 관리한다. 캐시는 마지막 수신본 조회에 쓰며 호스트 복구용 백업이나 원본으로 승격하지 않는다.
- 통신: Electron main의 전용 HTTPS 서버·클라이언트. renderer는 기존 제한된 preload를 통해서만 요청하며 Node·DB·인증 비밀에 접근하지 않는다.
- LAN에는 페어링·연결 상태·허용 자료 조회만 노출한다. 멤버용 공유 CRUD API를 만들지 않고, 로컬 IPC에서도 자료 출처와 역할을 검사한다.
- UI 버튼 숨김만으로 권한을 구현하지 않는다. 공유 자료의 복제된 로컬 ID를 개인 쓰기 API에 넣어 변경하는 경로도 거절한다.

### 최초 설정·역할 — Q21·Q23 확정

공유를 설정하지 않은 기존 사용자는 업데이트 후에도 개인 사용을 유지하며 네트워크 수신 포트를 자동으로 열지 않는다.
공유 설정에서 대표 PC는 ‘호스트로 사용’, 나머지는 ‘멤버로 연결’을 선택한다(Q21).
첫 버전은 대표 호스트 하나, 멤버당 연결 호스트 하나로 제한하고 호스트·멤버 동시 역할과 앱 내 호스트 이관은 제외한다(Q21).
설정 후 호스트↔멤버 역할 전환도 첫 버전에서는 제공하지 않는다(Q21). 공유 원본이 있는 호스트를 멤버로 바꾸며 원본을 암묵적으로 이동·삭제하지 않는다.
이 제한은 Q2의 예상 규모를 하드코딩하는 것과 다르다. 개인 전용 사용자에게 역할 선택을 강제하지 않는다.

호스트는 자기 개인 프로젝트의 참여자 이름을 기존처럼 편집한다. 멤버로 연결한 앱에서는 개인 프로젝트까지 참여자 편집을 숨기고 기존 이름을 읽기 전용으로 보존한다(Q9).
후속 사용자 확인: 프로젝트 참여자 추가·수정·삭제는 호스트만 제공한다. 아직 역할을 설정하지 않은 개인 전용 상태와 멤버 연결 해제 후의 개인 전용 상태에도 참여자 편집을 제공하지 않는다. 기존 이름은 삭제하지 않고 읽기 전용으로 보존한다.
개인 프로젝트·일정의 일반 편집과 참여자 관리는 별개 권한이다. 비호스트의 개인 프로젝트 수정에서도 기존 참여자 이름이 유실되거나 임의 변경되지 않도록 UI와 main 양쪽에서 보호한다.

역할은 최초 공유 설정에서 명시적으로 선택한 호스트/멤버 설정으로 구분한다. IP, 프로젝트 생성 여부, 접속 순서로 자동 판별하지 않는다.
작성자 기술안은 역할을 main이 관리하는 로컬 설정에 저장하고 renderer는 조회만 하는 것이다. 최초 역할 설정 요청은 별도 검증 경로를 거치며, 일반 자료 변경 요청의 역할 주장이나 UI 표시값을 권한으로 신뢰하지 않는다.
멤버를 선택해도 최초 승인이 끝나기 전에는 연결 대기 상태이며 공유 자료를 받지 못한다. 승인된 이후에도 호스트가 매 요청의 설치 자격·실제 IP·프로젝트 공유 대상을 검증한다.
현재 설계의 최초 역할 선택에는 별도 관리자 비밀번호나 조직 관리자의 호스트 지정 기능이 없다. 다른 독립 설치본이 별도 호스트를 설정할 수 있다는 것과 기존 호스트의 자료 관리 권한을 얻는 것은 다르다. 후자는 허용하지 않는다.
멤버의 명시적 ‘연결 해제’는 확인창을 거쳐 해당 호스트의 캐시·자기 공유 알림 설정/이력·접속 자격을 제거하고 개인 전용으로 돌아간다(Q23).
개인 자료는 유지한다. 같은 호스트에 다시 연결할 수 있지만 최초 승인을 다시 받고 공유 알림은 꺼짐으로 시작한다.
연결 해제는 호스트 역할로 바꾸거나 다른 호스트로 이관하는 우회 경로가 아니다. 역할 이력과 같은 호스트 식별에 필요한 비밀이 아닌 최소 정보는 접속 자격과 구분한다.
단순한 네트워크 끊김이나 공유 중지는 이 명시적 연결 해제와 다르며 캐시를 유지한다.

### 참여자와 설치본 연결 — Q22 확정

호스트가 공유 프로젝트에 참여자 이름·IP를 등록하고 승인된 설치본을 연결한다.
같은 PC를 여러 프로젝트에 등록할 수 있으므로, 승인 설치본은 호스트 내 공통 등록으로 관리하고 프로젝트별로 공유 대상을 선택한다(Q22).
첫 연결 승인 뒤 다른 프로젝트에도 같은 승인 PC를 추가하면 다시 코드 대조하지 않고 그 프로젝트만 추가로 허용한다.
공통 등록의 IP를 수정하면 해당 PC가 속한 모든 프로젝트에 적용하고 영향을 받는 프로젝트를 저장 전에 보여준다.
같은 실제 접속 IP를 서로 다른 승인 설치본에 중복 등록하지 않는다(Q22). 이름이 같다는 이유로 기존 자격과 자동 연결하지 않는다.
프로젝트에서 참여자를 빼면 그 프로젝트만 회수하고, 승인 PC 자체를 해제하면 해당 PC의 모든 공유 권한을 회수한다.

호스트 자신의 공유 자료 접근은 원본 소유자 권한이다. 호스트 자신의 IP를 참여자로 추가할 필요는 없다.
참여자 없는 새 공유 프로젝트는 호스트만 볼 수 있다. 기존 이름이 있는 개인 프로젝트의 전환에서는 Q20의 명시적 확인을 생략할 수 없다.

## 최초 연결·암호화·IP 검사

1. 호스트가 공유 기능을 설정하고 선택한 LAN 주소·포트를 표시한다. 멤버가 그 주소를 직접 입력한다. 자동 탐색·외부 중계는 제외한다.
2. 승인 대기 연결에서는 일정이나 설치 자격을 주고받지 않는다. 호스트 인증서 지문과 해당 시도에 결합된 확인값을 양쪽에서 대조한다.
3. 멤버의 호스트 신뢰 확인과 호스트의 참여자/설치본 승인 모두 완료된 뒤에만 충분한 난수 접속 자격을 발급한다. 발급 응답 유실은 업무 자료 공개 없이 페어링 재시도로 처리한다.
4. 이후에는 승인한 호스트 인증서·신원을 검사하고, 호스트는 매 요청의 자격·실제 소켓 IP·프로젝트 허용 목록을 확인한다. 요청 본문 IP나 전달 헤더는 신뢰하지 않는다.
5. IP 변경은 호스트가 수정한다. 인증서 변경·만료·설치 자격 소실은 자동 신뢰하지 않고 연결을 중단해 재확인/승인을 안내한다.

확인값을 서버가 보내 준 임의의 짧은 문자열로만 표시하지 않는다. 최초 연결에서는 양쪽이 독립 계산한 충분히 긴 인증서 지문과 페어링 시도 결합값을 비교하는 방식을 기본 기술안으로 둔다.
짧은 숫자 코드로 줄이려면 검토된 인증 프로토콜과 추측 방지 근거를 구현 계획에서 먼저 제시해야 한다.
페어링에는 만료·시도 횟수 제한을 두고, 승인 전에는 업무 자료·재사용 자격 전송을 차단한다.
최초 인증서 조사에 필요한 예외는 그 연결·상태에만 제한한다. 전역 TLS 검증 해제나 모든 인증서 허용은 금지한다.
승인 뒤 연결 전용 trust anchor, 인증서 유효기간·안정된 호스트 신원 검증, 인증서/키 핀을 적용한다. 호스트 주소와 인증서 신원은 분리한다.

호스트 개인키와 멤버 접속 비밀은 main에서 Windows safeStorage의 비동기 API로 보호한다. 호스트에는 멤버 자격의 검증용 해시를 저장한다.
이는 Windows 사용자 범위의 보호이지 같은 사용자 권한의 악성 프로그램이나 설치 폴더 복제에 대한 하드웨어 인증이 아니다.
복호화 실패 시 평문으로 강등하거나 새 자격을 자동 승인하지 않는다. 앱 데이터와 키를 보존한 재설치는 기존 설치 자격을 유지할 수 있으며, 키가 없는 PC 교체·프로필 초기화는 다시 승인한다.

작성자 기술안은 IPv4 직접 LAN 연결과 IPv4-mapped IPv6 주소 정규화를 우선 대상으로 한다. NAT·공유 프록시를 통한 여러 PC의 동일 출발지 IP는 대상이 아니다.
다중 네트워크 어댑터에서는 호스트의 수신 주소와 멤버의 실제 사용 주소를 보여준다. 방화벽을 자동으로 끄거나 광범위한 예외를 만들지 않는다.
제품 포트는 설정 가능하게 하고 기본값은 구현 계획에서 정한다. 이미 사용 중인 포트는 실패를 안내하며 임의 포트로 조용히 바꾸지 않는다.
회사 정책에 따른 포트 허용은 배포 검증 항목이며, 과거 8765 HTTP 성공으로 HTTPS 제품 연결 성공을 대신하지 않는다.

## 저장·원본 공유 전환

호스트의 기존 프로젝트·일정 ID를 유지한 채 공유 상태·참여자·공유 변경 정보를 같은 SQLite transaction으로 저장한다.
전환 전 참여자 이름·IP와 제거 대상을 확인한다. 전환 commit 뒤에만 공유 완료를 표시하고 개인 필터에서 제외한다.
일정·호스트 자신의 알림 설정·알림 전송 이력은 유지해 전환만으로 알림이 반복되지 않도록 한다.
실패하면 상태 전환과 참여자 변경 모두 rollback한다. DB 초기화·마이그레이션 실패 시 원본 보존·편집 차단 규칙도 유지한다.
별도 공유 DB로 복사 후 개인 DB에서 삭제하는 두 단계 전환은 채택하지 않는다.

멤버의 수신 자료·알림은 개인 자료와 구분된 테이블·타입으로 저장하는 안이다. 공유 키는 최소 `(hostId, datasetId, remoteEntityId)`로 식별한다.
현재 숫자 문자열 ID를 받는 개인 CRUD에 복합 문자열을 그대로 넘기지 않는다. 통합 화면에는 출처가 명시된 참조 타입을 쓰고 main에서 각 저장소로 분기한다.
개인 DB와 공유 캐시의 프로젝트 ID가 같아도 편집·접힘 상태·알림·선택이 섞이지 않아야 한다.
수신 DTO에는 호스트의 개인 프로젝트, 개인 알림 설정·전송 이력, 다른 PC의 접속 비밀·IP 목록을 포함하지 않는다.
참여자 표시 이름은 해당 공유 프로젝트의 읽기 전용 정보로 제공하되 접속 관리 정보와 분리한다.

공유→개인 역전환·공유 복사본 자동 생성·호스트 PC 자동 교체/이관은 첫 버전 범위에서 제외하는 제안이다.
‘공유 중지’는 서버 제공을 멈추는 것이며 공유 프로젝트를 개인 자료로 바꾸거나 삭제하지 않는다.

## 2초 확인·전체 수신·삭제와 회수

정상 연결 중에는 2초마다 겹치지 않게 확인한다. 현재 설치본이 볼 수 있는 자료와 권한만으로 만든 버전/ETag를 비교한다.
호스트 개인 자료나 다른 참여자에게만 보이는 프로젝트 변경이 이 버전에 나타나지 않도록 한다. PC 5개 멤버 기준 평균 약 2.5요청/초라는 계산은 부하 실측을 대신하지 않는다.
변경이 있으면 허용된 전체 공유 snapshot을 받는다. 최대 60개 예상 일정에서는 증분 로그·삭제 tombstone 없이 전체 수신을 기준으로 복구한다.

- 호스트는 자료와 허용 목록, 응답 버전을 일관된 DB 읽기 transaction에서 만든다. 호스트 자료·권한 변경은 commit된 결과만 응답한다.
- 멤버는 프로토콜·크기·형식·날짜·키 참조를 모두 검증한 뒤 캐시와 수신 버전을 같은 transaction으로 반영한다.
- 살아 있는 키는 UPSERT해 개인 알림과 이력을 유지한다. 모든 행을 DELETE 후 재삽입하지 않는다.
- 정상 snapshot에서 사라진 프로젝트·일정은 화면·캐시·해당 로컬 알림 설정/이력에서 제거한다. 프로젝트명 변경은 설정 초기화 사유가 아니다.
- 인증된 권한 회수 응답 또는 최신 허용 목록만 회수 근거로 사용한다. 빈 권한 목록은 정상적으로 모든 공유 자료를 제거할 수 있다.
- 네트워크 실패·인증서 실패·IP 불일치·버전 불일치·호스트 DB 오류를 빈 snapshot으로 바꾸지 않는다. 기존 캐시는 조회만 유지하고 연결 오류를 표시한다.
- 회수 반영은 정상 연결 시 다음 확인·수신에서 이루어진다. 물리적으로 즉시 전파된다는 보장은 아니며 5초 목표에 포함한다.
- 오프라인 캐시나 별도 복사본을 원격으로 즉시 지울 수 없다. 캐시 제거는 논리 삭제이며 디스크의 모든 잔존 바이트나 Windows의 과거 알림 기록 삭제를 보장하지 않는다.

초기 구현 제안은 요청 timeout 5초, 첫 확인 실패 즉시 연결 끊김 판정, 재시도 2→4→8→최대30초다.
화면에 마지막 정상 확인 시각을 표시하고 ‘다시 연결’은 즉시 시도한다. 재연결 성공 시 전체 최신 상태를 검증한 뒤 연결됨·알림 가능 상태로 바꾼다.
앱 시작·절전 복귀에서도 먼저 재검증하며, 정상 상태의 5초 반영 목표는 끊김 재시도 시간을 포함하지 않는다.

후속 사용자 요구로 멤버의 제목 표시줄에 수동 동기화를 제공한다. 자동 확인과 같은 인증·권한·검증 경로를 사용하되,
2초 주기나 재시도 대기를 건너뛰어 최신 허용 자료 전체를 요청한다. 변경 버전이 같아도 단순히 변경 없음으로 끝내지 않고 최신 자료를 받아 적용한다.
자동 확인·수동 동기화·알림 전 확인은 한 수신 경로에서 직렬화한다. 이미 실행 중인 요청 뒤에는 수동 전체 수신을 한 번만 예약하고,
연속 클릭으로 요청을 누적하지 않는다. 이전 응답이 새 결과를 덮어쓰지 않도록 한다.
완료는 수신 검증과 로컬 저장이 모두 성공한 때다. 개인 자료·미저장 입력·살아 있는 공유 일정의 자기 알림 설정/이력은 유지한다.
삭제·회수 항목에는 기존 제거 규칙을 적용한다. 실패 시 기존 수신본을 보존하고 성공 토스트를 표시하지 않는다.

프로토콜 버전이 호환되지 않으면 필요한 업데이트를 안내하고 캐시를 자동 삭제·부분 적용하지 않는다.
캐시 쓰기 실패는 공유 수신 실패로 처리하고 마지막 완전 수신본을 유지한다. DB 전체가 실패한 경우에는 기존 저장 오류 정책을 적용한다.

## PC별 공유 알림

- 멤버가 처음 받는 일정의 알림은 꺼짐이며 입력 기본값은 기존과 같은 2일 전·09:00이다. 각 PC의 설정과 전송 이력은 전송하지 않는다.
- 호스트의 공유 일정 알림도 자신의 로컬 설정이다. 개인→공유 전환에서는 기존 설정·처리 이력을 유지한다.
- 멤버는 네트워크가 끊겨도 자신의 알림 설정은 로컬에 저장할 수 있지만, 최신 권한·자료 확인 전에는 공유 알림을 보내지 않는 제안이다.
- 주기 확인 실패·절전 복귀·앱 재시작부터 재검증 완료까지 공유 알림을 중단한다. 발송 직전에 필요한 최신 확인을 공유 폴링 경로로 수행하며 실패·timeout이면 보류한다. 성공 응답 직후 물리 단절까지 완벽히 감지할 수는 없다.
- 재연결 후 오늘 놓친 미처리 알림만 제공한다. 과거 날짜를 쌓아 보내지 않고, 기존 중복 억제·결과 불명 자동 재전송 금지 규칙을 적용한다.
- 멤버의 알림 변경은 공유 일정 내용 변경이 아니며 호스트로 전송하지 않는다. 호스트 일정 날짜 변경 시 각 PC가 자신의 설정으로 예정일을 다시 계산한다.
- 날짜 변경 때문에 개인 알림 계산이 0001년 이전으로 벗어나면 해당 알림을 보류하고 설정 수정을 안내한다. 멤버 설정 오류가 호스트의 유효한 일정 수정 자체를 막지 않는다.
- 호스트는 원본 소유자이므로 공유 제공을 중지해도 자기 공유 일정 알림은 계속 평가하는 제안이다. 호스트 앱 완전 종료·절전 때는 기존 실행 조건이 적용된다.
- 삭제·회수된 자료의 미처리 알림은 중단한다. 수신 자료를 다시 허용받으면 제거된 개인 설정을 자동 복구하지 않고 기본 꺼짐으로 받는다.
- 알림 클릭 시 멤버는 읽기 전용 일정 상세와 자기 알림 설정을 연다. 기존 미저장 입력 보호를 유지하고 삭제·회수된 일정은 더 이상 열지 않는다.

## 화면·편집 계약

기존 C안 도구 모음·간트·달력·편집 패널을 유지한다. 별도 계정 로그인 화면은 추가하지 않는다.
개인/공유를 통합 표시하고 ‘전체 / 개인 / 공유’ 필터, 출처·조회 전용 표시, 공유 연결 상태와 마지막 정상 확인 시각을 제공하는 제안이다.
기본 필터는 전체로 두며 역할·연결 설정은 별도 공유 설정에서 관리한다. 필터로 숨겨도 해당 PC의 알림 권한이나 처리 여부는 바뀌지 않는다.

멤버 공유 프로젝트에서는 추가·이름/날짜 수정·삭제·드래그 이동/리사이즈를 차단한다. 공유 일정 상세의 자기 알림 설정은 별도로 저장할 수 있다.
개인 프로젝트의 동작은 유지한다. 날짜 빈칸 클릭 시 멤버의 공유 행에서는 새 공유 일정을 만들지 않으며 개인 프로젝트를 대상으로만 기존 추가 흐름을 제공한다.
필터 전환·항목 전환은 기존 미저장 입력 보호를 유지한다. 수신 갱신은 사용자가 작성 중인 개인 입력을 덮어쓰지 않는다.
공유 일정의 알림 설정 입력 중 날짜가 갱신되면 최신 날짜를 표시하되 입력값은 유지·재검증하고, 삭제/회수되면 입력 저장을 막고 종료를 안내한다.

### 멤버 제목 표시줄의 수동 동기화·연결 상태 — 후속 사용자 요구

멤버 화면에서 Planrail 제목과 최소화·최대화/복원·닫기가 있는 최상단 윈도우 바에 두 요소를 추가한다.
현재 [Titlebar](../../src/renderer/components/Titlebar.tsx)의 창 제어 버튼 왼쪽에 `수동 동기화 / 호스트 연결 상태 / 최소화 / 최대화 / 닫기` 순서로 배치하는 작성자 UI안이다.
호스트와 개인 전용 화면에는 멤버용 두 요소를 표시하지 않는다. 창 드래그 영역은 유지하되 조작 요소는 드래그 제외 영역으로 지정한다.

| 요소 | 계약 |
| --- | --- |
| 수동 동기화 버튼 | 새로고침 아이콘. 클릭하면 위의 즉시 전체 수신을 수행. 진행 중에는 진행 표시와 중복 실행 차단. 완료 후 기존 우측 하단 2초 토스트 규칙으로 알림 |
| 연결 상태 아이콘 | 호스트와 정상적으로 인증·자료 확인을 마치면 초록색. 접속 실패·인증/권한 오류·공유 중지 등 정상 동기화가 불가능하면 빨간색 |

색상 두 가지와 제목 표시줄 배치는 사용자 요구다. 세부 상태 처리는 다음 작성자 제안으로 전체 설계 검토에 포함한다.

- 초록색은 마지막 확인에서 해당 멤버의 공유 연결과 자료 상태가 정상임을 뜻한다. 단순 ping 성공이나 호스트 PC의 전원이 켜졌다는 의미가 아니다.
- 최초 연결 확인 전·승인 대기·앱 재시작·절전 복귀 시에는 빨간색과 ‘연결 확인 중/승인 대기’ 설명을 사용한다. 확인되지 않은 상태를 정상으로 표시하지 않는다.
- 정상 상태의 정기/수동 확인 중에는 직전 상태를 유지하고, 실패·timeout 또는 최신 상태 확인의 유효성 상실 시 빨간색으로 바꾼다. 단절 순간을 즉시 감지한다고 보장하지 않는다.
- 연결은 성공했지만 수신 검증·캐시 저장이 실패한 경우도 빨간색으로 표시하고 ‘동기화 실패’ 원인을 구분한다. 허용 프로젝트가 0개인 정상 응답은 연결 실패가 아니다.
- 연결 끊김에서도 수동 동기화로 즉시 재시도할 수 있다. 호스트 주소/자격이 없는 승인 대기 상태에서는 버튼을 비활성화하고 설정·승인이 필요함을 안내한다. 수동 버튼은 인증서 신뢰나 승인 절차를 우회하지 않는다.
- 두 아이콘에 접근 가능한 이름을 제공한다. 수동 동기화 설명과 연결 상태·마지막 정상 확인 시각은 마우스 오버/키보드 포커스 설명으로 확인할 수 있게 한다. 기존 툴팁 제한에는 이 두 공유 요소만 추가한다.
- 실패 안내는 확인 가능한 원인을 표시한다. 단순 접속 실패만으로 ‘호스트 PC 꺼짐’이라고 단정하지 않으며, 조치가 필요한 오류는 기존 지속 오류 안내를 사용한다.

## 실행·중지·종료

최초 호스트 공유 시작은 명시적으로 한다. 이후 마지막 공유 시작·중지 상태를 보존한다(Q24).
공유 중 앱을 종료했다면 다음 앱 실행 시 공유를 자동 재개하고, 명시적으로 공유를 중지했다면 중지를 유지한다.
앱 종료를 처리하며 서버를 닫는 것은 사용자의 공유 중지 선택으로 기록하지 않는다. 재개 시 인증·저장 초기화가 실패하면 실패 상태를 안내하고 자료를 제공하지 않는다.
트레이 숨김은 공유를 유지한다. 공유 중지·완전 종료는 신규 요청을 중단하고 진행 중 응답·로컬 저장을 정리한다.
가능한 경우 중지 상태를 응답하되 갑작스런 종료·전원 차단에도 안내 도착을 보장하지 않는다. 멤버는 다음 확인 실패로 단절을 판정한다.
X·Alt+F4의 트레이/완전 종료/취소와 트레이 종료의 미저장·진행 중 저장 보호는 유지한다.
서비스·로그인 자동 실행·자동 절전 방지는 추가하지 않는다. 멤버의 개인 편집은 호스트 상태와 독립적이다.

## 구현 계획에서 해결할 기술 항목과 근거

- 인증서 생성 라이브러리·번들·라이선스·Windows 호환성을 별도 검증해야 한다. Node `X509Certificate`는 인증서 읽기/검증 API이며 발급 API가 아니다. 설치 PC에 OpenSSL CLI가 있다고 전제하지 않는다.
- [`@peculiar/x509`](https://github.com/PeculiarVentures/x509)는 생성 API를 제공하는 조사 후보이며 아직 채택하지 않았다. 설치본마다 키를 생성하고 공통 개인키를 배포하지 않는다.
- [Node 24 TLS](https://github.com/nodejs/node/blob/v24.22.1/doc/api/tls.md)와 [HTTPS](https://github.com/nodejs/node/blob/v24.22.1/doc/api/https.md): 자체서명 인증서는 핀 콜백 추가만으로 기본 신뢰 검증을 통과하지 않는다. 최초 확인과 이후 trust anchor/핀 경로를 구분해야 한다.
- [Electron 45 safeStorage](https://github.com/electron/electron/blob/v45.2.1/docs/api/safe-storage.md): 비동기 API 사용 가능, Windows 사용자 범위 보호. 설치 버전의 내장 Node는 [공식 metadata](https://releases.electronjs.org/releases.json) 기준 24.22.1이다.
- 페어링 메시지·만료·시도 제한·TLS 재사용·해지된 자격 검사·응답 크기 제한·프로토콜 버전·DB migration 상세는 구현 계획의 검증 가능한 계약으로 만든다.
- 이 기술 조사로 실제 LAN 인증·성능·알림·방화벽 호환성이 검증된 것은 아니다.

| 기존 오프라인 앱 | 기존 전면 outbound 차단 개인 CRUD 회귀 유지. 별도 LAN 허용·인터넷 차단 환경에서 공유 테스트 |

실제 사내 Windows 6PC·TLS·방화벽·5초 목표·알림 수신은 **미검증**이다. 현재 변경은 설계 문서뿐이다.
문서 검사 결과와 builder 검토 후 추가 결정을 아래에 기록했다. 전체 설계 승인 전에는 구현을 시작하지 않는다.

## Builder 검토 후 확정된 운영 협의 Q21~Q24

독립 검토에서 Q1~Q20의 모순은 발견하지 않았으며, 남은 네 가지 운영 결정을 한 차례 협의했다.
사용자가 Q21~Q24의 추천안을 모두 선택하여 해당 제품 결정을 확정했다.

## 최종 검토 시 확인할 작성자 제안

사용자가 고른 제품 정책 외에 다음 기술·화면 선택을 제안했다. 개별 라이브러리/API 명세는 구현 계획에서 검증하며,
전체 설계 승인을 구현·Windows 실기 검증 완료로 해석하지 않는다.

- main의 HTTPS 통신, 승인 호스트 신뢰와 IP·설치 자격 검사, 수신자별 허용 snapshot만 전달.

- 전체/개인/공유 필터와 읽기 전용 상세, 멤버의 오프라인 개인 알림 설정 편집 허용·발송 보류.
- 멤버 제목 표시줄 수동 동기화·초록/빨강 상태 표시는 후속 사용자 요구로 추가. 구체적인 배치 순서·미확인 상태 설명·요청 직렬화는 작성자 제안.
