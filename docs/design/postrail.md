# PostRail 첫 버전 설계

2026-11-20 · Q12에서 첫 버전 범위와 화면 시안을 승인했다. 설계 협의의 기준 소스는 WorkRail `2be6647`이다. 원격 `39b3e86`의 배치·IPC 진입점과 충돌이 없는지 확인했다. 제품 구현은 후속 작업이다.

이 문서는 Q12 승인 당시 기준이다. 환경별 토큰 재사용과 최신 화면·동작의 구현 기준은 [PostRail 최종 승인 설계](postrail-workspace.md)에 기록했다.

## 목표

WorkRail 안에서 장비별 환경 변수를 바꿔가며 REST 요청을 직접 작성·전송하고 응답을 확인한다. 테스트 데이터를 여러 건 준비할 때는 POST 본문의 `${index}`만 회차별로 바꿔 반복할 수 있게 한다.

## 요청으로 확인한 범위

- 상단 도구 메뉴의 이름은 **PostRail**이다. Home·PlanRail·NodeRail·TermRail과 함께 제공한다.
- GET·POST·DELETE, URL, 헤더, 필요한 경우 JSON 객체 본문을 입력한다. 본문을 폼 데이터나 문자열로 한 겹 더 감싸지 않고 JSON으로 전송한다.
- 장비 주소, 로그인 계정, 비밀번호 등의 환경 변수를 정의할 수 있다. 본 요청 전에 해당 환경을 사용해 로그인하거나 토큰 인증을 준비할 수 있어야 한다.
- POST에 반복 횟수를 지정할 수 있다. 10회를 입력하고 실행하면 `${index}`를 회차별로 치환한 POST 요청을 보낸다. 문자열 보간은 JavaScript 객체 리터럴을 평가한다는 뜻이 아니다.
- 이번 작업은 설계와 화면 시안이다. 별도 구현 계획과 제품 구현은 사용자 요청 이후에 진행한다.

## 협의 기록

- Q1 확정: 첫 버전의 실행 전 단계는 로그인 요청, 응답에서 토큰 추출, 본 요청 헤더에 삽입을 설정으로 구성한다. Postman JavaScript 실행 및 호환은 첫 버전 범위에서 제외한다.
- Q2 확정: 요청과 환경은 이 PC에 이름을 붙여 저장하고 다시 열 수 있다. 비밀번호는 저장을 선택한 경우에만 보호 저장소에 저장한다. 로그인으로 얻은 토큰은 해당 실행에서만 사용한다.
- Q3 확정: 환경마다 로그인 설정 하나를 두고, 저장한 요청별로 실행 전 인증을 켠다. 로그인 응답의 JSON 경로에서 토큰을 꺼내 지정 헤더에 넣는다. 반복을 시작할 때 로그인은 한 번만 수행하며, 인증 또는 토큰 추출이 실패하면 본 요청을 발송하지 않는다.
- Q4 확정: 반복 POST는 순서대로 한 건씩 보낸다. 개별 회차에서 오류가 발생하면 오류를 회차별 결과에 남기고 다음 회차를 진행한다. 타임아웃 등 서버 반영 여부를 알 수 없는 회차는 ‘결과 확인 필요’로 표시한다. 실패한 회차는 자동 재시도하지 않는다.
- Q5 확정: 첫 실행의 인덱스는 1이다. 1~10을 돌린 뒤 같은 요청을 다시 실행하면 마지막 번호 다음인 11부터 시작한다.
- Q6 확정: 다음 번호는 저장한 요청에 속한다. 선택한 환경과 무관하며 저장한 요청을 다시 열거나 앱을 재실행할 때 유지한다.
- Q7 확정: 전송을 시도한 번호는 오류 또는 타임아웃이 나더라도 사용한 것으로 처리한다. 중지 요청을 받으면 진행 중인 한 건의 응답 또는 타임아웃까지 기다린 뒤 종료한다. 아직 발송하지 않은 번호부터 이어간다.
- Q8 확정: 반복 횟수에는 제품 차원의 고정 상한을 지정하지 않는다. 양의 정수를 받으며 기본값은 1회다. 이전 회차가 끝나기 전에 다음 회차를 시작하지 않는다.
- Q9 확정: HTTP와 HTTPS를 지원한다. HTTP는 평문 연결이라고 화면에 표시한다. HTTPS는 Windows가 신뢰하는 인증서만 허용하며 사내 CA도 이 규칙을 따른다.
- Q10 확정: 현재 실행 중 또는 마지막 실행의 회차별 결과와 선택한 회차의 응답을 조회한다. 긴 결과 목록은 나눠 표시한다. 다시 실행하거나 앱을 닫을 때 지난 결과를 장기 이력으로 보관하지 않는다.
- Q11 확정: `${index}`가 있는 1회 POST도 저장 요청의 다음 번호를 쓴다. 인덱스 없는 일반 1회 POST는 다음 번호를 바꾸지 않는다.
- Q12 확정: Q1~Q11과 작업 화면 시안을 승인했다. PostRail은 한 번에 한 실행만 진행한다. 현재 또는 마지막 실행의 결과에 요청 이름과 환경을 표시한다. 인덱스를 사용하는 요청은 먼저 저장하며, 인덱스가 없는 POST는 보내는 횟수와 관계없이 다음 번호를 바꾸지 않는다. 승인 범위는 설계다.

## 하나의 요청으로 보는 동작

환경의 장비 주소를 참조하는 POST 요청을 쓰고 JSON 탭에 다음을 입력한다.

```json
{
  "name": "test_${index}"
}
```

따옴표를 포함한 유효한 JSON이다. 처음 10회를 실행하면 `test_1`부터 `test_10`까지 차례로 발송한다. 다시 10회를 누르면 `test_11`부터 `test_20`까지 이어서 보낸다. 실행 전에 이번에 쓸 처음·마지막 이름을 표시한다.

예를 들어 네 번째 요청이 HTTP 409를 받으면 결과표의 4회차에 상태와 오류를 표시하고, 5회차부터 계속 발송한다. 로그인에 실패하면 본 요청 자체가 시작되지 않는다. 같은 요청에서 개발 환경으로 1~10을 실행한 뒤 QA 환경으로 바꾸거나 앱을 재실행해도 QA에서 11부터 보낸다. 그 전에 인덱스를 쓰는 POST를 한 건 보내면 그 한 건이 11을 사용하고, 다음 반복은 12부터다. 5번을 전송하는 중 중지하면 5번의 응답이나 타임아웃까지만 기다리고, 다음 실행은 6부터다.

## 요청과 환경의 입력

- 요청은 이름, 메서드, URL, 헤더, JSON 본문, 실행 전 인증 사용 여부를 보관한다. 환경 전환은 현재 편집기의 변수 해석과 인증 설정에 적용한다. 전송을 시작하면 선택한 환경과 입력값을 확정하고, 이후 편집은 다음 실행에만 반영한다.
- 환경에 이름과 변수 행을 둔다. URL의 `${deviceUrl}`, 본문 문자열의 `${username}`처럼 참조할 수 있다. JSON은 먼저 객체로 읽고 문자열 값 안에서 치환한 뒤 JSON으로 직렬화한다. 숫자·불리언·배열·중첩 객체 등 다른 값의 타입은 유지한다. 등록하지 않은 변수나 올바르지 않은 URL·JSON은 해당 입력란에서 설명한다. `index`는 예약 이름이다.
- 비밀값은 입력과 환경 목록에서 마스킹한다. 보호 저장소를 쓸 수 없으면 ‘이 PC에 저장’을 사용할 수 없으며, 사용자가 직접 입력한 값으로 현재 실행을 시작할 수 있다. 요청의 URL, 본문 또는 헤더에 비밀번호나 토큰을 적어 평문으로 저장하는 대신 보호 변수 참조를 사용한다.
- 메서드의 본문 입력은 POST를 기본으로 한다. GET에는 본문 입력을 끄고, DELETE는 서버에서 요구할 때 JSON 본문을 선택한다. POST 본문을 비워 보낼 수 있으며 JSON 본문을 입력한 경우 기본 Content-Type은 `application/json`이다.

## 실행 전 인증

환경 편집의 로그인 설정에 URL, 헤더, JSON 본문, 토큰 JSON 경로와 적용할 헤더를 둔다. 예를 들어 로그인 응답의 `data.token`을 읽고 본 요청의 `Authorization`에 `Bearer` 접두어와 함께 넣는다. 로그인 직후 토큰이 없거나 예상 타입이 아니면 인증 단계 실패를 표시한다. 본 요청 헤더에 같은 이름이 이미 있으면 덮어쓰지 않고 입력을 확인하도록 안내한다.

로그인 프로필의 토큰은 같은 환경의 대상 서버에만 전달한다. 인증이나 본 요청에서 다른 주소로 이동하라는 응답은 자동으로 따라가지 않고 화면에 표시한다. HTTP에서 비밀번호나 토큰을 보내려는 경우, 실제 주소와 평문 연결 표시를 전송 전에 보여준다. HTTPS 인증서 오류는 실패로 표시한다. 토큰 자체와 로그인 응답 원문은 결과나 진단 로그에 넣지 않는다.

## 반복 실행과 결과

- 반복은 저장한 POST 요청에서 사용한다. 요청을 복제하면 별도의 요청으로 보고 첫 번호는 1이다. 인덱스를 사용하는 1회 POST도 저장한 요청에서 실행한다. PostRail에서는 한 번에 하나의 실행을 진행한다. 사용자가 명시적으로 눌러 실행하고, 메뉴나 요청 목록을 이동해도 현재 또는 마지막 실행을 다시 볼 수 있다. 앱을 완전히 다시 시작하면 중단한 실행을 자동 재개하지 않는다.
- 중복 실행이 같은 요청의 번호를 두 번 사용하지 않도록 5번을 보낼 때 먼저 이 요청의 다음 번호를 6으로 저장하고, 저장이 완료된 뒤 5번을 보낸다. 저장 직후 앱이 비정상 종료되면 5번의 발송 여부를 알 수 없으므로 재사용하지 않는다. 실행 전 인증이나 입력 검증에 실패하면 본 요청의 번호는 그대로 둔다. 번호와 횟수는 큰 양의 정수에서도 반올림 없이 다룬다.
- 반복에 `${index}`가 없으면 동일한 요청을 여러 번 보낸다는 점을 버튼 옆에 표시한다. 인덱스를 쓰지 않는 POST는 횟수와 관계없이 저장한 요청의 다음 번호를 바꾸지 않는다. 인덱스가 있는 경우 시작·끝 이름 또는 번호를 표시한다. 진행 중에는 진행 건수와 중지 버튼이 보이며, 다음 회차를 시작한 뒤 이전 회차로 돌아가지 않는다.
- 실행 결과는 앱 세션에서 현재 또는 마지막 실행 한 건으로 관리한다. 결과에는 요청 이름과 사용한 환경을 함께 표시해 목록에서 다른 요청을 선택해도 어느 실행의 응답인지 알 수 있게 한다. 결과는 HTTP 성공, HTTP/전송 오류, 결과 확인 필요, 미전송으로 구분한다. 서버의 응답 상태, 본문·헤더, 소요 시간을 선택한 회차에서 확인한다. 대량 실행은 회차를 한 번에 화면에 펼치거나 모든 응답을 메모리에 쌓지 않는다. 다음 번호는 유지하고 실행 결과는 선택 조회가 가능한 임시 데이터로 관리한다. 결과를 표시할 수 없는 저장 오류가 나면 원인을 알리고 이후 발송을 중지한다.

## 화면 배치

- 왼쪽에는 이름 붙인 요청 목록, 환경 전환, 환경 관리 진입을 둔다. 같은 요청에서 환경을 바꾸면 주소·변수·로그인 설정에 새 환경이 적용되고 다음 번호는 그대로 보인다.
- 상단에는 메서드·URL·보내기와 반복 횟수를 둔다. 보내기 버튼에 이번 횟수를 표시하고, 버튼 아래에서 다음 번호 또는 치환 범위를 확인한다. 전송 중에는 진행률과 중지를 같은 위치에서 제공한다.
- 중앙 왼쪽은 헤더·JSON 본문·실행 전 설정, 오른쪽은 응답 본문·헤더와 상태다. 반복 결과 목록은 아래에서 열고, 선택에 따라 오른쪽 응답이 달라진다.
- 기존 WorkRail의 차콜 배경과 얇은 패널 경계, 하늘색 동작 버튼을 사용한다. URL·JSON에만 고정폭 서체를 적용한다. 응답 성공과 오류는 상태 문구와 색으로 함께 표시한다.

## 기존 구조와 적용 경계

- [상단 도구 메뉴](../../src/renderer/workrail/ToolDock.tsx)와 [앱 진입점](../../src/renderer/App.tsx)의 화면 전환을 따른다. 환경은 PostRail에서 요청을 구성하는 데이터 묶음이다. NodeRail의 Windows·WSL 실행 환경과 별개다.
- [창 정책](../../src/main/window.ts)과 [preload](../../src/preload/index.ts)를 기준으로 화면과 권한을 분리한다. 화면은 요청 편집과 결과 표시를 담당하고, 실제 HTTP 전송과 보호된 값 처리는 앱 메인에서 담당하는 방향이다. 응답은 JSON 또는 텍스트로 표시하며 HTML을 실행하지 않는다.
- [TermRail 시작 파일](../../src/main/termrail/startup-files.ts)의 로컬 보호 저장 방식이 참고점이다. PostRail의 비밀번호와 토큰의 보존 범위는 Q2를 따른다.

## 첫 버전 범위

| 구분 | 범위 |
| --- | --- |
| 첫 버전 필수 | GET·POST·DELETE, URL과 헤더, JSON 객체 본문, 환경 전환, 로그인·토큰을 위한 실행 전 단계, POST 인덱스 치환, HTTP 상태·응답·반복 결과 |
| 첫 버전 확정 추가 범위 | 요청·환경의 로컬 저장, 선택적 비밀번호 보호 저장, 환경별 로그인·요청별 인증 사용, 오류 표시 후 다음 회차 진행, 요청별 번호 이어가기, 횟수 상한 없음, HTTP·HTTPS, 현재 또는 마지막 실행 결과 조회 |
| 후속 후보 | 다른 HTTP 메서드·본문 형식, Postman 컬렉션 가져오기, 실행 기록·팀 공유, 병렬 실행, Postman JavaScript 호환. 후속 후보의 제공 여부는 별도 협의한다. |

## 첫 버전 인수 기준

- GET·POST·DELETE에서 서버에 도착한 메서드와 헤더를 확인한다. JSON 본문의 속성·중첩 객체·배열의 타입이 유지되어야 한다. 치환으로 생긴 따옴표나 줄바꿈도 JSON 문자열에서 올바르게 처리한다.
- 정의되지 않은 변수나 유효하지 않은 JSON은 발송 전에 오류를 표시한다. 로그인 응답에 필요한 토큰이 없으면 실행 전 단계 실패를 표시한다.
- 격리된 테스트 서버에서 POST 10건의 이름이 서로 다르고, 회차별 상태와 완료·중단·미전송 건수를 구분할 수 있어야 한다. 시간을 초과한 POST가 서버에 반영됐는지 불명확할 때 자동 재시도 대신 상태를 표시한다. 4회차 실패 뒤 5~10회차가 실행되는지, 같은 요청의 다음 10회가 11~20인지 확인한다.
- 앱 재실행·환경 전환 이후에도 같은 요청은 11부터 이어져야 한다. 중지할 때 진행 중인 회차만 마무리하고, 다음 실행은 미전송 번호부터 이어져야 한다. 인덱스가 있는 1회는 번호를 전진시키고 인덱스가 없는 1회·반복은 번호를 보존한다. 전송 직전 비정상 종료 시 예약한 번호를 재사용하지 않는지 확인한다.
- 테스트 환경에서 101회 입력을 제한하지 않고 순차 실행한다. 더 큰 양의 정수는 실제로 그만큼 전송하지 않고 입력 검증·범위 표시·중지 동작을 확인한다.
- HTTP 화면에서 평문을 표시하고, 신뢰하는 사내 인증서와 신뢰할 수 없는 인증서를 구분한다. 실행 전 인증이나 인증서 검증에 실패하면 해당 본 요청이 서버에 도달하지 않아야 한다. 반복 중지는 이미 진행 중인 1건의 결과까지 기록한다.
- 보호된 값과 실행 토큰은 기본 화면·오류·복사·진단 로그에 노출하지 않는다. 저장을 선택하지 않은 비밀번호는 앱을 다시 열면 남지 않아야 한다.

## Q12 이후의 추가 결정

창의 ×로 트레이에 숨겨도 실행을 계속한다. 트레이에서 ‘앱 종료’를 선택하면 다음 회차 발송을 멈추고, 이미 진행 중인 한 건의 응답 또는 시간 초과를 기다린 뒤 종료한다. 인증 중에 종료를 요청했으면 본 요청을 시작하지 않는다.

환경마다 토큰을 받을 API 주소를 하나 명시한다. 로그인 주소는 달라도 된다. 변수 치환을 마친 요청의 프로토콜·호스트·유효 포트가 등록한 API 주소와 일치할 때만 토큰을 붙인다. 인증을 켠 요청의 대상이 다르면 발송 전에 주소를 확인하도록 안내한다. 리디렉션은 자동으로 따라가지 않는다.

응답 대기 시간은 공통 기본값을 사용하며 요청별로 조정할 수 있다. 실행을 시작할 때 적용값을 확정한다. 시간 초과 회차는 기존 규칙대로 ‘결과 확인 필요’로 남긴다. [재검토 결과와 화면 시안](postrail-review.md)
