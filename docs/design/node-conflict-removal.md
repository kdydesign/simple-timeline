# Node 환경 충돌 — 기존 Node 제거와 nvm 설치 확정 설계

> 2026-11-18 후속 실행 요청: 사용자가 문서 정리 후 설계 반영 시작을 명시했다. 본 설계를 구현 기준으로 적용하며 과거의 구현 전·코드 수정 금지 표기는 당시 협의 이력이다. 현재 진행·검증은 [구현 기록](../implementation/2026-11-18-workrail-polish-and-recovery.md)을 따른다.

2026-11-18. 상태: **Q6 전체 설계 확정**, Q1~Q5 사용자 선택 및 독립 설계 검토 완료. 사용자는 “이 내용으로 설계는 확정하고 코드 수정은 하지마”라고 명시했다. 당시 작업은 설계 문서 확정까지였다. 이후 명시된 구현 요청으로 제품에 반영했으며 현재 검증 범위는 상단 기록을 따른다.
기준 소스: WorkRail 1.0.0 `1ad2882`. 기존 [통합 도구 설계](team-tool-expansion.md)의 Q8 수동 정리 정책을 이번 요청 범위에서 확장한다. 기존 구현과 이번 제안을 구분한다.

## 요청과 목적

nvm-windows가 없고 기존 Node.js 설치가 충돌하는 PC에서, 사용자가 브라우저와 Windows 설정을 찾아다니지 않고 WorkRail의 안내와 버튼을 통해 제거 및 nvm 설치를 이어간다.

- 충돌 경로와 영향 안내, **기존 Node.js 제거** 버튼을 제공한다.
- 제거는 사용자 클릭으로 시작한다. 파일·폴더를 직접 삭제하지 않고 Windows의 공식 제거 절차를 사용한다.
- 제거 후 환경을 다시 확인하고 **nvm-windows 설치** 버튼을 제공한다. 제거와 설치는 별도 사용자 동작이다.
- 기존 글래스 재질·색상과 Node 목록 중심 화면을 유지한다.
- 후속 메뉴 변경은 [통합 도구 설계의 Q10](team-tool-expansion.md#q10-변경-반영-기준--상단-탭-b)을 따른다. 주 앱의 메뉴는 D 하단 도크에서 B 상단 탭으로 변경하도록 확정했다. Node 충돌 카드·제거·설치 흐름은 해당 Node 관리 화면에 적용하며, 독립 관리 창에 전체 도구 메뉴를 추가하는 요청은 아니다. 메뉴 변경도 설계만 반영하며 제품 구현은 시작하지 않는다.

## 현재 구현에서 확인한 사실

- [discovery.ts](../../src/main/node-management/discovery.ts)의 `standalone-node`는 PATH에서 선택되는 실행 후보에 관한 진단이다. 해당 파일을 공식 MSI 제품이 소유한다는 증거가 아니다.
- [NodeScreen.tsx](../../src/renderer/workrail/NodeScreen.tsx)는 충돌이 있을 때 설치 버튼을 숨기고 수동 정리 안내만 표시한다.
- [service.ts](../../src/main/node-management/service.ts)는 작업 직전 재검사, 작업 직렬화, 종료·업데이트 보호, 작업 후 재검사를 이미 수행한다. 현재 제거 명령은 없다.
- [windows.ts](../../src/main/node-management/windows.ts)의 승격 결과 처리는 nvm 작업용이다. MSI에도 존재하는 1610·1611을 내부 신호로 사용하므로 제거 결과를 그대로 연결할 수 없다.
- 개발 실행은 시스템 Node의 electron-vite와 개발 서버에 의존한다. 설치본 Electron의 자체 런타임과 구분한다.

## 검토한 접근

- 공식 MSI만 직접 제거 / 수동 설치와 다른 관리 도구까지 제거: 사용자는 공식 MSI 범위를 선택했다. 나머지 설치 방식에는 원래 관리 도구에 맞는 안내를 제공한다.
- Windows 표준 제거 UI / WorkRail 내부 무음 진행: 사용자는 표준 UI를 선택했다. WorkRail은 제거 프로그램을 실행하고 결과를 재검사하는 역할을 맡는다.
- 설치본에서만 제거 / 개발 실행에서도 제거: 사용자는 개발 실행 지원을 선택했다. 개발 호스트 Node의 제거에 대한 별도 진행·복구 경로가 필요하다.
- 현재 개발 창 유지 / 독립 관리 창으로 인계: 사용자는 독립 관리 창을 선택했다. 기존 프로세스의 BrowserWindow만 추가하면 개발 서버 종료에 함께 영향을 받으므로 별도 Electron 프로세스와 정적 화면 자산이 필요하다.

## 확정된 흐름과 기본값

다음은 Q6에서 전체 설계로 승인한 흐름이다. 제품의 현재 구현과는 구분한다.

1. 최신 환경 검사에서 nvm 미설치와 기존 Node 충돌을 확인한다.
2. 충돌 실행 파일과 공식 MSI 설치 제품의 대응이 명확한 단일 대상이면 제거 버튼을 활성화한다. 대상이 불명확하면 버튼을 비활성화하고 이유·수동 안내·재검사를 제공한다.
3. 같은 안내 카드에 nvm 설치 버튼도 표시하되, 충돌이 남아 있으면 비활성화하고 기존 Node 제거가 먼저 필요하다고 설명한다.
4. 제거 클릭 시 제품 버전·경로·Node와 npm 사용 중단·전역 도구의 재설치 가능성을 확인한다. 취소하면 아무 작업도 시작하지 않는다.
5. 개발 실행이면 먼저 독립 관리 창의 준비와 작업 인계를 확인하고 그 창에서 대상·영향을 확인한다. 설치본은 현재 화면에서 확인한다. 사용자 확인 후 대상 정보를 다시 검증하고 Windows 표준 제거 UI를 연다. WorkRail 전체를 관리자 권한으로 바꾸지 않는다.
6. 종료 결과와 실제 환경을 모두 확인한다. 제거 프로그램의 종료만으로 제거 완료나 nvm 설치 가능을 선언하지 않는다.
7. 제거 완료 및 충돌 해소가 확인되면 nvm 설치 버튼을 활성화한다. 사용자 클릭으로 기존 공식 1.2.2 설치 지원을 사용한다.
8. nvm 설치가 확인되면 공식 Node 목록에서 버전 설치 및 사용 선택을 이어간다. 터미널·VS Code는 PATH 반영을 위해 다시 열어야 할 수 있다.

### 화면 문구와 버튼

레이아웃·추가 동작은 에이전트 제안으로 작성했으며 Q6의 전체 문서 승인에 포함된다. 별도 시안이 승인된 것으로 간주하지 않는다.

충돌 카드의 제목은 **Node 환경 충돌**로 유지한다. 본문은 “기존 Node.js가 설치되어 있어 nvm-windows와 충돌합니다. 기존 Node.js를 제거한 뒤 nvm-windows를 설치해 주세요.”로 제안한다. 확인한 버전·설치 경로를 함께 표시한다.

| 단계 | 주 동작 | 함께 표시할 안내 |
| --- | --- | --- |
| 제거 가능한 공식 MSI 확인 | 기존 Node.js 제거 | nvm-windows 설치는 비활성, 기존 Node 제거 후 사용 가능 |
| 개발 실행에서 제거 클릭 | 별도 관리 창 열기·준비 상태 | 관리 창에서 제거를 확인하며, 준비 실패 시 제거하지 않음 |
| 제거 확인 | 제거 진행 / 취소 | 대상 버전·경로, Node·npm 사용 중단, 전역 도구 백업·재설치, 실행 중인 작업 저장·종료 안내 |
| Windows 제거 UI 진행 | 진행 상태 | WorkRail의 중복 변경 버튼 비활성, 취소는 Windows 제거 화면에서 수행 |
| 제거 완료·충돌 해소 | nvm-windows 1.2.2 설치 | 제거 완료 표시, 설치 프로그램 완료 후 환경 확인 |
| 제거 완료·잔여 충돌 | 환경 다시 검사 | 잔여 경로별 해결 안내, nvm 설치 비활성 |
| nvm 설치 완료 | Node 버전 선택·설치 | 기존 공식 목록·검색·설치된 버전 사용 동작 재사용 |
| 새 Node 사용 확인 | 관리 창 닫기 | 새 터미널에서 개발 명령을 다시 실행하도록 안내 |

공식 MSI를 확인하지 못하면 제거 버튼을 이유와 함께 비활성화한다. 수동 안내를 주 동작과 중복해서 항상 노출하지 않고, 직접 지원할 수 없는 상태와 설치 다운로드 실패의 대안으로 제공한다.

## 개발 실행의 독립 관리 창

사용자가 개별 선택한 것은 개발 실행 지원과 별도 관리 창이다. 아래 프로세스·자산·복구 설계는 이를 충족하기 위한 에이전트의 기술 제안으로 작성했고 Q6에서 전체 설계로 승인했다.

### 준비와 인계

- 개발 서버를 사용하지 않는 유지보수 전용 main/preload/HTML 엔트리를 제공한다. Node 관리와 이번 제거 기능만 사용하며 Planrail DB·공유·알림·앱 업데이트 서비스를 초기화하지 않는다.
- 제거 전에 검증된 Electron 런타임과 정적 관리 화면 자산을 개발 watcher 출력·프로젝트 node_modules와 분리된 사용자별 유지보수 디렉터리에 준비한다. 실행 중 덮어쓰지 않는 버전별 디렉터리를 사용한다. 복사 완료·자산 일치·실제 기동을 확인하지 못하면 제거하지 않는다.
- 시스템 Node·npm·Vite·localhost URL 없이 해당 Electron 실행 파일을 직접 실행한다. 개발용 Node 옵션, 디버그 포트, ELECTRON_RUN_AS_NODE 등 불필요한 환경을 전달하지 않는다.
- 개발 프로세스와 수명이 독립된 프로세스로 실행하고 자체 프로필·single-instance lock을 사용한다. 기존 사용자 DB 프로필을 공유하지 않는다. 중복 실행은 기존 관리 창으로 연결한다.
- 관리 창의 준비 확인과 작업 소유권 인계가 끝난 뒤 관리 창이 대상을 다시 탐색한다. 부모가 전달한 경로·명령·ProductCode를 실행 권한으로 신뢰하지 않는다.
- 대상이 확인 화면과 달라지면 확인을 무효화한다. 단순 작업 실행 인계로 제거 확인을 생략하지 않는다.
- 부모 개발 창이 살아 있으면 “별도 관리 창에서 Node 환경을 설정하고 있습니다”와 창 열기 동작을 표시하며 Node 변경 동작을 막는다. Planrail 작업은 기존 서비스가 살아 있는 동안 유지한다.

### 관리 창 수명과 복구

- 관리 창은 제거·nvm 설치·Node 설치/사용을 사용자별 단계로 제공한다. 다음 단계를 자동 실행하거나 기존 Node를 자동으로 재설치하지 않는다.
- 제거 전에 Node 없이 실행 가능한 재진입 바로가기를 준비하고 위치를 보여 준다. 사용자 시작 메뉴의 WorkRail Node 환경 복구 항목과 관리 창의 위치 열기를 제안한다. 관리 창을 닫거나 PC를 재부팅해도 이 경로로 다시 진입할 수 있어야 한다. 자동 시작 등록은 하지 않는다.
- 진행 중인 설치·제거가 있으면 관리 창을 숨길 수 있으나 정상 종료와 자산 정리는 보류한다. Windows 제거 UI의 취소 동작을 가로채거나 강제 종료하지 않는다.
- 작업이 없으면 창을 닫을 수 있다. Node 미설치 상태라면 개발 명령을 아직 실행할 수 없고 복구 바로가기로 돌아올 수 있음을 안내한다.
- 단계·대상 식별 정보·확인한 프로세스 정체성·MSI 종료 코드·재부팅 대기를 최소한의 복구 기록으로 남긴다. npm 설정 내용·토큰·환경변수 전체는 기록하지 않는다. 기존 확인을 재시작 후 자동 승인으로 재사용하지 않는다.
- 재진입 시 기록된 성공 상태를 그대로 믿지 않고 설치 제품·파일·PATH·작업 프로세스를 다시 확인한다. 실행 중인 작업이 끝났다는 근거가 없으면 중복 변경을 막는다. 재부팅이 필요했던 경우 실제 부팅 세션 변경을 확인한 뒤 재검사한다.
- 복구 런타임·자산·바로가기는 후속 진입을 위해 보존하며 사용자 프로필의 일반 권한으로만 실행한다. 새 작업에서 교체할 때도 실행 중 자산은 삭제하지 않는다. 개발 프로젝트 파일을 제거·정리하지 않는다.
- 개발 서버·다른 Node 앱은 자동 종료하지 않는다. 제거 화면이 파일 사용 중을 알리면 사용자가 작업을 저장하고 해당 프로세스를 닫거나 취소하도록 한다. 개발 서버의 자동 재시작도 범위 밖이다.

### 여러 프로세스의 동시 변경 방지

- 기존 메모리 내 barrier만으로는 두 프로세스를 보호할 수 없다. 설치본·개발본·개발 멤버·관리 창의 모든 Node 변경 경로가 같은 Windows 장치에서 동일한 작업 잠금을 사용하도록 확장한다. 다른 CLI가 수행하는 변경까지 통제한다고 주장하지 않는다.
- 관리 창 single-instance lock과 Node 변경 작업 잠금은 구분한다. 잠금 소유자·승격 작업의 실제 수명이 불명확하면 시간이 지났다는 이유만으로 새 제거·설치를 시작하지 않는다.
- 관리 창과 주 앱 사이의 상태 신호는 사용자·세션·상대 프로세스와 연결해 검증한다. 상태 메시지는 제거 권한을 부여하지 않는다. 중요한 작업 전에는 항상 실제 환경을 재검사한다.
- OS 잠금/IPC 수단, 제한된 접근 권한, 복구 기록의 저장 형식은 구현자가 정하되 부모 종료·helper 비정상 종료·UAC 작업 생존을 검증하는 계약 테스트가 필요하다.
- standalone Node 제거가 주 앱을 종료시킬 수 있으므로 단지 주 앱 프로세스가 끝났다는 이유로 전체 작업 잠금을 해제하지 않는다. 앱 업데이트·실제 종료 보호는 관리 창의 작업 상태를 함께 고려한다.

## 범위와 비목표

Windows x64의 nvm 미설치 + 기존 Node 충돌이 진입 조건이다. 이미 nvm이 설치된 환경의 Node 제거, Node 버전 일괄 삭제, ZIP·타 버전 관리자 제거, 전역 npm 자동 이관, PATH 자동 청소, 임의 잔여 폴더 삭제, 다른 프로세스 강제 종료, 자동 재부팅은 포함하지 않는다.

Node·npm이 잠시 없는 상태는 설치 전환의 정상 중간 상태다. 공식 제거 프로그램이 사용자 설정·전역 도구를 전부 보존한다고 약속하지 않는다. 전환 전 사용자가 백업을 판단할 수 있도록 안내하며, 실패 시 자동 롤백을 제공하는 설계가 아니다.

## 설치 식별과 권한 경계

- 화면에 표시한 경로, 제품 이름·publisher 문자열만으로 제거 대상을 확정하지 않는다. 공식 MSI 제품 정보와 실제 node.exe 컴포넌트 경로·파일 정체성을 교차 확인한다.
- Node MSI의 `Uninstall` 등록에 `InstallLocation`이 반드시 있다는 가정을 하지 않는다. 공식 소스의 설치 경로 기록과 MSI 컴포넌트 경로를 조사 근거로 삼는다.
- main에서 대상을 식별한다. renderer가 경로·ProductCode·명령 문자열을 지정해서 제거할 수 있는 API를 만들지 않는다. 확인 이후 대상이 바뀌면 다시 확인한다.
- 검증한 시스템 `msiexec.exe`와 검증한 ProductCode에 고정된 제거 인수를 사용한다. 레지스트리의 임의 `UninstallString`을 실행하지 않는다. 권한 상승 이후에도 대상 일치를 확인한다.
- MSI 등록과 컴포넌트 경로 외에도 공식 출처의 근거를 검증한다. 승인된 공식 제품 계열 정보 및 실행 파일/설치 패키지의 서명·무결성 등 구현에서 채택한 증거가 부족하거나 불일치하면 수동 안내로 내려간다. 지원 가능한 공식 MSI의 버전·설치 scope와 실제 근거는 구현 전 조사·fixture 목록으로 고정해야 하며 임의의 Node.exe를 실행해서 신뢰하지 않는다.
- 시스템 msiexec의 `/x`와 검증된 ProductCode, `/norestart`, 자동 앱 종료 억제를 위한 `MSIRESTARTMANAGERCONTROL=Disable`을 검토 기준으로 삼는다. 표준 제거 UI의 파일 사용 중 동작은 Windows에서 확인한다. `/quiet`나 `/passive`로 사용자 취소 경로를 없애지 않는다.
- 승격 bridge의 오류와 실제 MSI 종료 코드는 구분된 결과 구조로 전달한다. 숫자 1610·1611을 서로 다른 의미로 혼용하지 않는다.
- 관리 창에도 sandbox·contextIsolation·정확한 로컬 URL/main frame 검사와 제한된 preload API를 적용한다. 제거 확인에는 main이 생성한 대상 스냅샷과 결합된 일회성 식별자를 사용하고 최신 일치 여부를 재검증한다.
- 재부팅을 자동 요청하지 않는다. MSI의 재부팅 필요 결과는 별도 상태로 처리한다.
- nvm 작업과 제거는 직렬화한다. 작업 중에는 기존 종료·앱 업데이트 보호를 유지한다. 다른 Node 프로세스나 사용자 앱을 임의 종료하지 않는다.
- 기존 폴더·PATH·npm 설정의 잔여물이 있으면 재진단하고 안내한다. 제거 성공을 이유로 임의의 잔여 폴더 삭제나 PATH 정리를 수행하지 않는다.

| --- | --- |
| 제거 성공, 제품 제거·충돌 해소 확인 | nvm 설치 활성화 |
| 제거 성공, 잔여 충돌 존재 | 잔여 경로·수동 해결·재검사 안내, nvm 설치 비활성 |
| 사용자 취소 또는 UAC 취소 | 취소 표시 후 환경 재검사, 실제 상태에 맞춰 버튼 표시 |
| 다른 Windows 설치 진행(1618) | 기존 작업을 마친 뒤 다시 시도하도록 안내, 자동 재시도 없음 |
| 재부팅 필요(3010) 또는 재부팅 시작(1641) | nvm 설치를 보류하고 재부팅·재검사 안내 |

## 인수 조건과 검증 계획

제품 구현 전 확인할 기술 항목은 실제 지원 MSI fixture와 서명 정책, 복구 프로세스의 Windows 수명, 장치 작업 잠금이다. 이 문서의 미확정 기술 세부는 사용자 요구사항을 축소하는 근거로 쓰지 않는다. 요구사항을 만족할 수 없다는 조사 결과가 나오면 구현 계획 단계에서 그 근거를 드러낸다.

| 조건 | 확인할 결과 |
| --- | --- |
| 정상 MSI + nvm 미설치 | 경로·버전·제거 버튼 표시, 표준 제거 UI, 실제 제거 후 nvm 설치 활성화 |
| 사용자/UAC 취소·제거 실패 | 성공 표시 없음, 환경 재검사, 적절한 재시도·수동 해결 안내 |
| MSI 작업 중·결과 유실 | 중복 요청 차단, 종료 불명 상태 유지, 원인 기록 |
| 재부팅 필요 | nvm 설치 차단, 재부팅 후 복구 바로가기로 진입·환경 재확인 |
| 제거 후 잔여 폴더·PATH 충돌 | 파일 자동 삭제 없음, 문제 경로와 수동 해결 안내 |
| ZIP·다른 관리자·불일치·복수 제품·shim | 제거 실행 안 함, 이유 표시 |
| 확인 후 대상 또는 nvm 설치 상태 변경 | 기존 확인 무효화, 새 검사 필요 |
| 개발 서버 종료·Node 파일 사용 중 | 독립 관리 창 생존, 무관한 프로세스 강제 종료 없음 |
| helper 준비 실패·불완전 자산 | 제거가 시작되지 않음 |
| Node 미설치 상태에서 창 종료·재부팅 | Node/npm 없이 복구 창 실행, nvm→Node 설치·사용 가능 |
| 여러 앱/개발 프로필/세션에서 동시 변경 | 하나만 수행, 다른 창은 상태 안내, 종료된 부모만 보고 잠금 해제하지 않음 |
| 관리 창 신뢰 경계 | renderer 임의 경로·명령·외부 프레임 요청 차단, sandbox 유지 |

단위/UI 검사는 진단·상태·문구·확인 취소·인계 실패를 검증한다. 격리 Electron E2E는 관리 창의 로컬 자산·IPC·프로필 분리·주 창 종료 후 진행을 검사한다. 실제 Windows 일회성 VM에서 공식 MSI 제거와 설치·UAC·재부팅·개발 실행의 수명 검증을 별도로 수행한다. 사용자의 실제 Node 설치나 운영 DB를 자동 테스트에 사용하지 않는다.

이 문서는 Windows 실기 성공이나 구현 완료의 근거가 아니다. 사용자의 코드 수정 금지 요청에 따라 이번 작업은 설계 확정으로 종료한다. 구현 계획·제품 코드 변경은 후속 요청이 있을 때 진행한다.

## 설계 검토 기록

2026-11-18 독립 검토자는 구현 계획을 막는 중요한 미답 질문이 없다고 판단했다. Node가 없는 재부팅 후 복구, 독립 관리 창 인계, 권한 경계와 작업 잠금 수명이 Q1~Q5와 충돌하지 않음을 검토했다. 이 검토는 실제 MSI 제거·UAC·부모 종료 독립성의 실행 검증이 아니다.

2026-11-18 Q6에서 사용자가 전체 설계를 확정했다. Q1~Q5의 사용자 선택과 화면·복구·검증에 대한 에이전트 제안을 포함한다. 사용자는 코드 수정 금지를 함께 명시했으므로 설계 승인을 구현 승인으로 해석하지 않는다.
