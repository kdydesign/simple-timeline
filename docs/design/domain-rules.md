# 도메인·날짜 규칙

작성일: 2026-11-03. 스테이지 1 산출물.
상태: 사용자 승인 완료. 업무 규칙과 문서 확인을 마쳤으며 제품 구현은 후속 단계다.
기준: main `4c2c6f4ba60b4b54ed066b21cc2b91e2a5f4d500`.

## 목적과 범위

오프라인 Windows 개인용 일정 관리에서 프로젝트·일정·참여자와 날짜의 의미를 고정한다.
후속 단계가 같은 데이터로 간트와 달력을 만들 수 있도록 계산·검증·정렬의 기대 결과를 명시한다.
기존 [전체 설계 기준](../superpowers/specs/2026-11-03-simple-timeline-design.md)의 사용자 확정사항은 유지한다.
이 문서가 스테이지 1 세부 규칙의 기준이며, 전체 설계의 스테이지 1 미결정 목록을 해소한다.

이번 단계에는 제품 코드, 의존성 설치, DB·IPC 구조, 화면 배치, 구현 계획을 포함하지 않는다.
시간대에 따라 일정 날짜가 바뀌거나 저장 실패가 성공·빈 데이터로 보이는 결과를 허용하지 않는다.

## 검토한 접근과 선택 근거

사용자는 2026-11-03 이 채팅의 다섯 질문 모두 추천안을 선택했다.
다음 대안 중 선택된 규칙을 아래에 구체화했다.

| 논점 | 선택한 접근 | 대안과 비교 |
| --- | --- | --- |
| 날짜 | 시간대 없는 날짜, 양 끝 포함 | 시각으로 환산하면 시간대·서머타임에 따라 날짜가 이동할 수 있다. 종료일 제외는 사용자에게 보이는 종료일과 기간 계산이 어긋난다. |
| 이름 | 중복 허용, 내부 식별자로 구분 | 중복 금지는 동일한 프로젝트명·단계명을 재사용하기 어렵게 한다. 표시상 구분 방식은 화면 설계에서 다룬다. |
| 참여자 | 입력 순서 유지, 빈 항목 제외, 동일 이름 중복 제거 | 원문 그대로 저장하면 공백 항목과 중복이 남는다. 계정·동명이인 식별 체계는 MVP 범위를 넘는다. |
| 정렬 | 프로젝트 생성 순, 일정 시작일·종료일·생성 순 | 이름순은 이름 수정에 따라 위치가 바뀌고, 일정 생성 순만 사용하면 날짜 흐름이 드러나지 않는다. |
| 조회 기준 | 실행마다 현재 월, 실행 중 선택 유지 | 마지막 연월 영구 복원은 선택하지 않았다. 선택 월로 간트를 제한하는 방식은 기존 전체 범위 요구와 맞지 않는다. |

## 프로젝트·일정·참여자

- 프로젝트는 일정을 묶는 상위 단위이며 이름·표시 색상·선택적인 참여자 이름 목록을 가진다.
- 일정이 없는 프로젝트도 존재하고 표시된다. 프로젝트 자체의 별도 시작일·종료일은 두지 않는다.
- 일정은 정확히 하나의 프로젝트에 속하고 이름·시작일·종료일을 가진다.
- 일정 기간은 서로 겹칠 수 있다. 개발·QA·배포의 순서나 의존성을 강제하지 않는다.
- 프로젝트 삭제는 확인 후 소속 일정과 함께 처리한다. 저장·삭제 성공은 실제 저장 성공 후 반영한다.
- 참여자는 프로젝트에 기록한 이름이며 계정·권한·일정 담당자가 아니다. 같은 이름의 서로 다른 사람은 구별하지 않는다.

## 필수값과 이름 정리

- 프로젝트명·색상, 일정명·시작일·종료일은 필수다. 색상은 기본값을 제공한다.
- 프로젝트명·일정명은 앞뒤 공백을 제거한다. 그 결과가 빈 문자열이면 저장을 거부한다.
- 이름 안쪽 공백과 대소문자는 보존한다. 프로젝트명과 일정명은 각각 중복을 허용하며 항목의 정체성은 내부 식별자로 구분한다.
- 참여자는 선택이다. 목록 각 이름의 앞뒤 공백을 제거하고 빈 항목은 제외한다.
- 정리된 문자열이 완전히 같은 참여자 이름은 첫 항목 하나만 남긴다. 나머지 항목의 입력 순서는 유지한다.
- 대소문자·내부 공백이 다른 참여자 이름을 임의로 합치지 않는다.
- 생성·수정 입력에 같은 규칙을 적용한다. 참여자 목록 정리는 오류로 취급하지 않는다.

색상 표현 형식과 기본 색상 값, 입력 화면의 목록 편집 방식은 후속 저장·화면 설계에 맡긴다.
이번 승인에 근거하지 않은 이름 길이 제한이나 추가 업무 제약을 요구사항으로 만들지 않는다.

## 업무 날짜와 기간

- 날짜는 서기 0001~9999년의 그레고리력 실제 날짜다. 연도 0000은 허용하지 않는다.
- 표현은 정확히 `YYYY-MM-DD`다. 빈 값·존재하지 않는 날짜·시각/시간대가 붙은 값은 허용하지 않는다.
- 시작일은 종료일보다 늦을 수 없다. 같은 날 시작·종료는 허용하며 1일이다.
- 날짜가 잘못되면 자동으로 다른 날짜로 보정하지 않고 저장을 거부한다.
- 시작일과 종료일을 모두 포함한다. 기간 일수는 두 날짜 사이의 달력상 일수 차이 + 1이다.
- 날짜의 전후·일수·월 경계 계산은 PC 시간대와 서머타임에 영향을 받지 않아야 한다.
  현지 자정 간 밀리초 차이를 24시간으로 나누는 계산에 의존하지 않는다.
- 윤년은 4의 배수인 해 중 100의 배수를 제외하되 400의 배수는 포함한다.
- 생성·수정 시각은 업무 날짜와 별개이며 [저장 설계](storage.md)의 UTC ISO 형식을 따른다.

## 기본 정렬

- 프로젝트는 생성 순서 오름차순이다.
- 각 프로젝트 안의 일정은 시작일 오름차순 → 종료일 오름차순 → 생성 순서 오름차순이다.
- 위 값이 모두 같은 경우 내부 식별자로 순서를 고정한다. 식별자의 구체 형식·비교 방식은 저장 구조에서 정한다.
- 이름·참여자·색상 수정은 생성 순서를 바꾸지 않는다. 일정의 날짜 수정은 날짜 정렬에 반영된다.
- 이 규칙은 프로젝트 목록과 프로젝트 안 일정 목록의 기본 순서다.
  달력의 겹친 일정 배치, 간트 행의 구체 표현, 사용자 정렬 UI를 이번 단계에서 추가하지 않는다.

## 전체 범위와 선택 연월

- 일정이 있으면 모든 프로젝트에 속한 전체 일정의 가장 이른 시작일과 가장 늦은 종료일을 사용한다.
- 간트는 가장 이른 시작일이 속한 월의 첫날부터 가장 늦은 종료일이 속한 월의 마지막 날까지 표시한다.
  중간에 일정이 없는 월도 포함한다. 일정 없는 프로젝트는 범위 계산에 날짜를 제공하지 않지만 표시된다.
- 전체 일정이 0개이면 간트는 선택한 연월 한 달 전체를 표시한다. 프로젝트가 0개인 경우도 같다.
- 선택 연월은 달력에서 보는 월을 뜻한다. 최초 실행과 앱 재실행에서는 PC 현지 날짜의 현재 월로 시작한다.
- 실행 중 모드 전환과 프로젝트·일정 추가/수정/삭제는 선택 연월을 자동 변경하지 않는다.
- 일정이 생기거나 날짜가 바뀌면 간트 범위는 전체 데이터로 다시 계산한다. 마지막 일정을 삭제하면 선택 연월 한 달로 돌아간다.
- 선택 연월이 간트 전체 범위 밖이어도 선택값을 바꾸거나 간트 범위를 자르거나 늘리지 않는다.
- 달력은 선택 월과 일정의 포함 기간이 겹치면 해당 월의 겹친 부분을 표시 대상으로 삼는다.
  이전 달에 시작하거나 다음 달에 끝난 일정도 누락하지 않는다.
- 선택 월 이동·범위 밖 탐색·스크롤·포커스는 [화면 설계](experience.md), 달력 주 경계 배치는 [시각화 계약](visualization.md)을 따른다.

## 승인과 후속 단계

사용자 확정 근거: 날짜 규칙은 ‘추천안 전체 적용’, 이름은 ‘중복 이름 허용’, 참여자·정렬은
‘추천안 적용’, 빈 데이터·선택 연월은 ‘재실행 시 현재 월’을 선택했다.
문서 확인 요청 후 사용자는 2026-11-03 ‘구현 진행해’라고 답했다.
이를 제시된 설계 문서의 승인과 요청 범위인 스테이지 1 마무리 진행 지시로 반영했다.
승인 당시에는 스테이지 1 설계만 마무리했으며 이후 구조·화면·구현은 각 단계에서 진행했다.
현재 날짜·입력·정렬 구현은 [domain](../../src/domain/), 기대 사례의 자동 검증은 [unit](../../tests/unit/)에 있다.
현재 실행 범위와 결과는 [검증 안내](../harness/validation.md)를 따른다. 설계 승인 기록 자체는 실행 증거가 아니다.
구현자는 위 업무 규칙을 바꾸지 않는 내부 함수·알고리즘을 선택할 수 있다.
