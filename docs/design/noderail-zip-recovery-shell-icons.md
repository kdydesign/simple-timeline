# Windows Node ZIP 설치, 작업 재검사와 WorkRail 셸 아이콘

2026-11-19 사용자 협의를 반영해 구현한 설계. 문제 조사 당시 소스는 `6510c935`이다. [구현 및 검증 기록](../implementation/2026-11-19-windows-node-zip.md)

## NodeRail에서 공식 ZIP으로 설치

Windows의 ‘설치’는 WorkRail이 선택한 Node 버전의 공식 Windows x64 ZIP을 검증해 기존 nvm의 버전 폴더에 등록한다. ‘사용’은 사용자가 따로 눌렀을 때 기존 nvm으로 전환한다. 사용자와 협의한 Windows x64 검증 시작 버전은 nvm-windows 1.1.10이다. 1.1.10과 팀에서 사용하는 1.1.11을 각각 검증하고, 이후 버전도 해당 버전에서 설치와 전환을 확인한 뒤 직접 ZIP 설치를 활성화한다. 2.x는 저장 구조를 별도로 검증해야 하고 WSL2는 배포판별 nodenv/node-build 설치 경로를 사용한다. [기존 환경별 지원 설계](workrail-environments-and-home.md)

1. 앱의 메인 프로세스가 선택한 환경의 nvm과 버전 저장 루트를 다시 확인한다. 공식 목록에 해당 버전의 Windows x64 ZIP이 있어야 설치할 수 있다. 화면에서는 버전과 환경 식별자만 받는다.
2. 지원하는 사내 프록시 설정과 인증서 검증을 적용해 공식 배포 경로의 ZIP과 해당 버전의 서명된 SHA-256 목록을 받는다. 신뢰하는 Node 릴리스 키로 서명을 확인하고 **정확한 ZIP 파일명**에 해당하는 해시와 대조한다. 기존 EXE/MSI 검증과 별개의 ZIP 검증이 필요하다. 프록시 실패, 서명·해시 오류, 쓰기 권한 부족, 확인된 보안 제품 차단은 구분해 안내한다. 차단 시 작업을 종료한다. [기존 프록시 범위](noderail-proxy-and-loading.md) · [공식 배포 목록](https://nodejs.org/dist/)
3. 같은 볼륨의 전용 임시 폴더에 압축을 푼다. 압축 경로 이탈, 링크·재분석 지점, 비정상적인 해제 크기를 거부한다. 배포본의 최상위 폴더를 한 번 벗겨 최종 위치가 `<nvm 버전 저장 루트>\v<버전>\node.exe`가 되게 한다. 배포본에 포함된 npm 구성도 확인한다.
4. 확인을 마친 폴더를 최종 이름으로 한 번에 이동하고 nvm이 해당 버전을 인식해야 설치 완료로 표시한다. 정상 설치된 동일 버전은 그대로 사용한다. 기존 불완전 폴더가 있으면 경로를 알려 주고 보존한다. 실패 시 이번 작업이 소유한 임시 자료만 정리한다. 등록 직후 목록 확인에 실패하면 실제 폴더와 nvm 목록을 재검사해 상태를 판별한다.

설치 진행 화면에는 ‘다운로드 중 → 무결성 확인 중 → 설치 중 → 설치 목록 확인 중’을 표시한다. 설치 전후 현재 사용 버전은 같아야 한다. 각 nvm 검증 대상에서 승인된 네트워크 경로로 내려받은 뒤, 새 버전이 `nvm list`에 나타나는지, 선택 전까지 기존 Node가 활성 상태인지, 별도 ‘사용’ 후 `node -v`와 `npm -v`가 해당 배포본과 일치하는지 확인한다.

## ‘환경 다시 검사’로 실패한 작업 복구

격리 재현에서 자동 환경 조회가 진행 중인 시점에 설치를 시작하면, 늦게 끝난 조회가 앱 자신의 작업 잠금을 외부 작업처럼 기억할 수 있었다. 설치 명령이 실패해 실제 파일 잠금이 풀렸어도 다음 ‘사용’ 요청이 거절됐다. 별도로, 자동 조회가 진행 중이라는 이유만으로도 같은 안내가 발생했다. 설치 결과는 모의 응답, 잠금은 실제 임시 파일을 사용했다. 사용자 PC에서 어느 경로로 발생했는지는 미확인이다. [Windows 작업 서비스](../../src/main/node-management/service.ts) · [작업 잠금](../../src/main/node-management/mutation-lock.ts)

‘환경 다시 검사’를 누르면 현재 선택한 환경의 작업 소유권·종료 결과·설치 목록·사용 버전을 다시 읽는다. 사용자가 누른 재검사와 창 포커스 복귀 시 자동 조회를 구분하고, 이전 조회 결과가 새 작업 상태를 덮지 않도록 환경과 작업 세대를 대조한다. 자동 조회 중의 ‘사용’ 요청은 조회 완료 후 대상 환경·버전·실제 작업 상태를 재확인한다.

| 재검사 결과 | 사용자가 보게 될 동작 |
| --- | --- |
| 이전 작업 종료 확인, 실제 잠금 해제, 환경 조회 성공 | 남아 있던 진행 레이어·이전 오류를 닫고 ‘설치’와 ‘사용’을 다시 활성화한다. 이전 실패 원인은 진단 기록에 남긴다. |
| 현재 앱 또는 다른 창의 실제 설치·전환 진행 중 | 해당 작업과 진행 상태를 표시하고 중복 실행을 막는다. |
| 다른 프로세스의 작업 종료 여부 미확인, 재부팅 필요 | 원인과 다음 조치를 표시한다. 잠금 소유권은 유지한다. |
| 환경 조회 자체가 실패 | 새 실패 원인을 표시하고 다시 검사할 수 있게 한다. |

Home, NodeRail, 독립 관리 창에 같은 판정 기준을 적용한다. 단순 시간 경과나 PID 조회 실패만으로 잠금을 삭제하지 않는다. WSL2는 선택한 배포판의 기존 복구 정책을 적용하며 조회를 위해 종료된 배포판을 자동 시작하지 않는다. 회귀 검증은 자동 조회와 설치 실패의 순서를 제어해 진행한다. 재검사 후 앱 재시작 없이 ‘사용’이 한 번 성공하는 경우, 실제 설치 도중 재검사를 눌러도 이중 실행되지 않는 경우, 다른 환경의 작업에 영향을 주지 않는 경우를 포함한다.

## 시작 메뉴와 작업 표시줄 우클릭의 이전 아이콘

사용자가 이전 아이콘을 본 위치는 시작 메뉴의 **모든 앱 또는 검색 결과**, 그리고 실행 중인 WorkRail의 **작업 표시줄 우클릭 메뉴**다. 동일 경로 업그레이드 후 세 화면을 각각 확인한다. 시작 메뉴의 고정 항목은 추가 회귀 검사에 포함한다.

문제 조사 당시 소스 ICO의 기존 6개 크기는 모두 새 그림으로 바뀌었고 20·40·128px가 추가됐다. 창은 기존 앱 ID와 설치 EXE의 아이콘 인덱스 0을 사용한다. 같은 경로에 업그레이드하면 기존 시작 메뉴 바로가기가 보존될 수 있다. 최신 Windows 빌드는 성공했지만 artifact 다운로드가 HTTP 403으로 끝나 배포 EXE의 리소스는 직접 대조하지 못했다. [패키지 설정](../../electron-builder.yml) · [작업 표시줄 속성](../../src/main/taskbar-details.ts) · [해당 CI 실행](https://github.com/kdydesign/simple-timeline/actions/runs/44478029589)

| 확인 순서 | 수정 및 인수 기준 |
| --- | --- |
| 실제 설치된 EXE | 같은 제품 버전의 여러 빌드를 구분하도록 릴리스 SHA를 확인한다. 설치된 EXE의 첫 아이콘 그룹을 추출해 16·32·48px 등 크기별로 새 원본과 대조한다. 다르면 패키징 단계에서 수정한다. |
| 시작 메뉴 ‘모든 앱’·검색 | WorkRail이 만든 바로가기의 대상, 아이콘 위치·인덱스와 앱 ID를 검사한다. 구버전 참조면 해당 바로가기만 갱신하고 Windows에 변경을 알린다. |
| 시작 메뉴 ‘고정됨’·작업 표시줄 우클릭 | 기존 핀을 둔 채 같은 경로에 업그레이드한다. 고정 항목과 실행 중 WorkRail 우클릭 메뉴의 **앱 이름 옆 아이콘**을 확인한다. 바로가기와 실행 창의 재실행 아이콘 참조가 같아야 한다. 아이콘 내용의 SHA-256을 파일명에 포함한 ICO를 두 위치에서 공통으로 참조한다. 아이콘 디자인이 바뀌면 Windows가 새 경로에서 그림을 읽는다. |

일회성 Windows 사용자로 신규 설치와 구 아이콘 빌드에서의 동일 경로 업그레이드를 각각 확인한다. 패키지 테스트에는 실제 설치 EXE의 아이콘 리소스와 바로가기 속성을 추가한다. 실제 셸 표시까지 확인해야 시각 문제를 해결한 것으로 기록한다. 기존 앱 ID·실행 파일명·사용자 핀 배치를 보존하고, 시스템 전체 아이콘 캐시 삭제나 Explorer 재시작에 의존하지 않는다. [기존 셸 아이콘 정책](release-notes-and-confirmations.md)
