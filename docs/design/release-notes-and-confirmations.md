## 목적과 범위

제목 표시줄에서 정보 기능과 창 제어를 구분하고, 사용자가 버전별 변경을 앱 안에서 읽을 수 있게 한다. 실제 일정 저장·삭제 직전에 확인하여 오조작을 줄인다. 도움말 최초 열기13초는 지연 구간을 조사하며 사전 준비를 늘려 해결된 것으로 처리하지 않는다. 작업표시줄 우클릭의 앱 항목에도 현재 아이콘을 연결한다.

개인/공유 권한·날짜 규칙·DB 보존·업데이트 배포 구조는 유지한다. [0.8.4 설계](editing-navigation-and-help.md)의 미저장 초안 무조건 폐기와 주 창 X의 트레이 숨김은 그대로다. 이번 확인은 초안 폐기 확인이 아니라 실제 저장/삭제 확인이다.

## 접근 방식과 선택

- 릴리즈노트 창은 닫을 때 파괴하는 방식과 숨겨 재사용하는 방식을 비교했다. Q6에서 재사용을 선택했다. 재열기는 빠르지만 창을 연 뒤에는 추가 메모리를 사용한다. Q7에 따라 첫 클릭 전에 자동 생성하지 않는다.
- 내용은 커밋 원문을 나열하지 않고 버전 경계·구현 기록으로 검증해 사용자 설명으로 작성한다. 사용자 지정 Conventional Commits 유형을 적용하며 내부 테스트 보정을 제품 버그 수정으로 오기하지 않는다.
- 도움말 조기 병렬 준비는 최초 대기를 주 화면 로딩과 겹칠 수 있으나 시작 시 경쟁·메모리 비용이 증가한다. 사용자는 이를 선택하지 않았다. 기존 ui-ready+1초 사전 준비/숨김 재사용은 유지하고 진단을 우선한다.
- 창만 먼저 보이는 방식은 본문 준비 지연을 없애지 못한다. 빈 창 표시를 성능 개선 근거로 삼지 않는다. 보안 격리 해제·GPU 강제 비활성화·Windows 보안 설정 변경은 이 근거로 도입하지 않는다.

## 제목 표시줄과 외곽

순서: **릴리즈노트 아이콘 → 도움말 아이콘 → 세로선 → 최소화 → 최대화/복원 → 닫기**.

릴리즈노트는 문서 모양 아이콘과 접근성 이름/툴팁 ‘릴리즈노트’를 사용한다. 기존 도움말 아이콘·툴팁은 유지한다. 구현자 제안은1px 두께·18px 높이의 비상호작용 구분선이며 Tab 대상이 아니다. 버튼은 창 드래그 영역에서 제외한다. 현재40×34px 조작 영역과 키보드 조작을 유지한다.

`src/renderer/forest-crystal.css`의 `#root { border: 1px solid var(--window-border) }`만 제거한다. 패널/버튼의 구분용 border와 배경 투명도, 창 크기 조절 기능은 유지한다.

## 릴리즈노트 창·콘텐츠

확정된 독립 창·오프라인·재사용을 위해 도움말과 같은 읽기 전용 창 보안 구조를 따른다. 구현자 제안:1120×800 논리 크기를 모니터 작업 영역 안에 제한하고, 왼쪽 버전 목록/오른쪽 변경 내용으로 구성한다. 처음에는 설치 버전의 노트를 선택하고 실행 중 마지막 버전·스크롤을 기억한다. 최신 버전부터 내림차순으로 정렬하며 설치 버전을 표시한다. 자동 다운로드·외부 문서 연결·업데이트 후 자동 팝업은 추가하지 않는다.

노트의 단일 원천을 검증 가능한 로컬 구조화 콘텐츠로 두고 앱에 포함한다. 릴리즈 시 현재 정식 버전 항목이 존재하는지, 버전 중복/정렬/빈 항목/참조 경로를 검사한다. 제품 버전과 무관한 ‘테스트용 다음 버전’은 정식 출시 내역에 포함하지 않는다. 출시일을 표시한다면 실제 배포 근거가 확인된 날짜만 사용하고 문서 작성일을 임의로 출시일로 쓰지 않는다.

Q2에서 승인한 예제:

```markdown
# Planrail 0.8.3

## Feat · 기능 추가
- 새 업데이트 발견 시 Windows 알림 제공
- 트레이에 ‘전체 알림 끄기’ 메뉴 추가
- 호스트에서 멤버 연결 상태와 마지막 접속 확인 시각 표시

## Fix · 오류 수정
- 트레이 최초 표시 시 자동 실행 체크 상태가 잘못 보이던 문제 수정

## 사용 안내
- 멤버도0.8.3 이상으로 업데이트해야 새 기능을 사용할 수 있습니다.
- 전체 알림을 꺼도 동기화와 UPDATE 버튼은 유지됩니다.
```

`Perf · 성능 개선`, `Docs · 도움말/문서`는 해당하는 실제 변경이 있을 때만 표시한다. 근거는 [0.8.3 구현 기록](../implementation/2026-11-16-notification-controls-and-presence.md) 등 기존 버전별 기록과 커밋을 대조한다. 설계만 승인된 기능이나 미검증 성능 목표를 제공 기능·달성 결과로 적지 않는다.

도움말과 릴리즈노트의 읽기 상태·창 생성·표시 상태는 별도로 관리한다. X로 명시적으로 닫은 노트는 주 창 복원 때 다시 나타나지 않는다. 트레이 숨김 직전 열려 있던 창만 함께 복원한다. 창별 최소화는 독립이며 앱 Exit/설치 종료 때 모두 정리한다. 주 창 초안에는 영향을 주지 않는다.

## 실제 저장·삭제 확인

| 행동 | 확인 내용 | 취소 |
| --- | --- | --- |
| 일정 추가 | 일정명·프로젝트·시작/종료일, ‘일정을 추가하시겠습니까?’ | 입력 유지 |
| 일정 수정 | 일정명과 변경되는 항목, 날짜 변경은 전후 날짜, ‘일정을 변경하시겠습니까?’ | 입력 유지 |
| 일정 삭제 | 일정명·기간, ‘일정을 삭제하시겠습니까?’ | 기존 일정 유지 |
| 드래그 이동/리사이즈 | 일정명·변경 전후 시작/종료일 | 원래 날짜·막대로 복원 |
| 알림만 변경 | 대상 일정·변경할 N일 전/시각/시작·종료 설정, ‘알림 설정을 변경하시겠습니까?’ | 입력 유지 |
| 프로젝트 삭제 | 프로젝트명·함께 삭제될 일정 수, ‘프로젝트를 삭제하시겠습니까?’ | 프로젝트/일정 유지 |

구현자 판단:

- 필드 유효성 검사를 먼저 수행하고 잘못된 입력은 기존 필드 오류를 보여준다. 유효한 저장 요청만 확인창을 연다.
- 기존 일정/프로젝트 편집 삭제 확인을 재사용해 이중 확인을 만들지 않는다. 일정 내용과 알림을 함께 저장하는 경우도 하나의 확인으로 묶는다.
- 확인 대기 중에는 저장 진행 표시/DB 쓰기/공유 변경 알림을 시작하지 않는다. 확정 뒤 기존 저장 보호·중복 제출 방지·성공 토스트·실패 안내 경로를 사용한다.
- 확인 대상으로 캡처한 ID·정규화된 입력을 사용하고, 확정 시 현재 접근 권한·대상 존재·저장 가능 상태를 재검사한다. 확인 중 공유 회수/저장 차단이 생기면 저장하지 않고 현재 오류를 안내한다.
- 드래그 확인은 유효한 날짜에 놓았을 때만 표시한다. Escape·무효 영역·입력 중단은 기존 취소. 확인 중 예상 위치는 미저장임을 구분하고 취소/실패 시 원본으로 복원한다. 데이터 변경이 없는 이동은 저장 요청을 만들지 않는다.
- 취소 버튼·Escape·X는 모두 취소로 처리한다. 기존 Dialog의 포커스 포획·복원을 유지하고 자동 복원만으로 툴팁이 열리지 않게 한다.
- 멤버는 기존처럼 공유 원본을 변경/삭제할 수 없다. 알림 설정 확인이 원본 변경 권한을 부여하지 않는다.

## 도움말 실측과 원인 조사

사용자 제공 로그는0.8.4, win32, main 기준 ms이다. 기록 시각은2026-11-17 08:44:09.666 KST (`2026-11-16T23:44:09.666Z`).

| 단계 | main 기준 ms |
| --- | ---: |
| prepare-start |18071|
| window-created / load-requested |18119|
| dom-ready / first-paint-ready |32868|
| 첫 클릭(prepared) |19761|
| 표시 |32886|
| 본문 준비 완료 |32942|

창 생성48ms, 로딩 요청→DOM/첫paint14,749ms, 클릭→표시13,125ms, 클릭→본문13,181ms. 클릭 전에 사전 준비가 시작됐고 완료 전에 클릭했다. 첫paint 이후 표시18ms·본문 준비까지74ms여서 주요 지연은 로딩 요청~DOM 준비 구간이다. 이 자료는 Chromium/renderer 시작, preload, 파일 읽기, JS 평가, 회사 보안 프로그램 중 원인 하나를 특정하지 못한다. 현재 도움말은 로컬 HTML/코드/이미지만 사용하며 인터넷에서 내용을 내려받는 기능은 없다.

Q7에 따라 초기 준비 순서/부하를 늘리지 않는다. 다음은 구현 시 원인 조사를 위한 진단 제안이며 성능 수정 완료가 아니다.

1. `help-latest.json`을 버전이 있는 진단 스키마로 확장: 문서·스크립트·스타일 요청 시작/완료/실패, navigation responseEnd/DOM 시점, preload 진입/준비, 도움말 모듈 실행·화면 준비 시점.
2. main·navigation·preload 시계의 원점과 단위를 명시한다. 도착 시간과 실제 실행 시간을 구분하고 다른 시계의 숫자를 직접 빼지 않는다. 누락/지원되지 않는 계측을0ms 성공으로 처리하지 않는다.
3. URL·파일명·IP·사용자명·일정/도움말 내용·검색어는 기록하지 않는다. 숫자·제한된 유형만 저장하고 요청/열기 기록 수와 관찰 시간을 제한한다. 기록 실패가 창 표시/편집을 차단하지 않는다.
4. `file://` Resource Timing은 누락될 수 있으므로 해당 창의 webRequest를 함께 관찰한다. 주 창·도움말·릴리즈노트 관찰기가 서로 덮어쓰지 않도록 webContents별 필터와 session별 소유권/해제를 보장한다.
5. 사용자 Windows에서 완전 종료 후 첫 열기/닫고 재열기/열린 창 호출, 같은 실행의 주 창 시작 기록을 함께 비교한다. 세부 로그로도 원인이 불명확하면 한정된 추가 trace 조사를 제안하고 원인을 추정해 설정을 바꾸지 않는다.

기존 창1초·본문3초는 목표로 유지하되 현재 관찰은 미달이다. 실제 렌더러 시작 자체의 단축과 이미 준비한 창의 재사용을 구분한다. 진단만 추가한 릴리즈에는 ‘도움말 최초 실행 지연 해결’이라고 쓰지 않는다. 원인별 성능 수정은 증거 확보 후 설계/계획에 반영한다.

## 작업표시줄 아이콘

현재 창·EXE·설치 아이콘 소스는 모두 현재 파란 P 아이콘을 가리킨다. 그러나 작업표시줄 재실행 항목의 `setAppDetails` 정보는 명시하지 않고 기존 설치의 바로가기와 Shell 캐시가 남을 수 있다. 사용자 PC의 원인은 미확정이다.

구현자 제안은 기존 AppUserModelID를 유지하면서 main 창의 재실행 이름·정확한 실행 파일/인수·현재 아이콘 위치를 명시하고, 설치본 EXE 및 생성/갱신 바로가기의 `IconLocation`을 검증하는 것이다. Windows Shell이 읽을 수 있는 안정된 실제 파일을 사용하고 ASAR 내부 경로를 지정하지 않는다. dev 실행에는 개발 환경 실행 경로를 별도로 처리하거나 설치 전용 설정을 제한하여 잘못된 재실행 명령을 만들지 않는다.

사용자의 기존 고정 항목을 임의 제거/재고정하거나 전체 Windows 아이콘 캐시를 삭제하지 않는다. 기존 고정 항목만 오래된 아이콘이 남는다면 새 실행과 기존 고정 항목을 구분해 안내한다. 설치 테스트 성공을 실제 사용자 작업표시줄 표시 성공으로 확대하지 않는다.

## 검증·완료 기준

- UI: 제목 구분선·아이콘 순서/툴팁/키보드·root border, 모든 저장/삭제 경로의 단일 확인·취소·유효성·권한·중복 제출·저장 실패 검증.
- Electron: 두 정보 창 동시 열기, 각각1개 유지, 첫 클릭 생성/닫기 재사용, 트레이·Exit·UPDATE 종료, 주 창 초안 보호, 별도 읽기 전용 IPC·외부 탐색 차단.
- 릴리즈 내용:0.8.0~0.8.4 및 현재 정식 버전의 실제 변경 근거·분류·버전 정렬·빈 분류 숨김·오프라인 포함 여부.
- 도움말: 기존 사전 준비 시점 회귀 없음, 진단 필드·시계·개인정보 제외·observer 해제·로깅 실패 비차단. 회사 PC 첫 열기/주 창 성능은 실제 자료가 있어야 판정.
- Windows: 새 설치/업데이트 EXE 리소스·바로가기 아이콘 정보·재실행 대상, 실제 우클릭 항목 아이콘은 사용자 PC 확인 항목.
- 구현 후 verify:app·harness·Windows 설치 CI를 실행한다. 현재 단계에서는 제품 코드·의존성·설치 설정을 변경하지 않는다. 전체 설계 승인 후 계획 작성·구현으로 진행한다.

## 남은 확인

Q8에서 전체 문서와 구현자 제안을 승인받았다. 원인 미확정인 도움말 성능은 진단과 성능 수정을 분리해 보고한다. 독립 builder check에서 구현 계획을 막는 추가 미답 질문은 없다고 확인했다. 승인 후 구현 계획에 따라 진행한다.
