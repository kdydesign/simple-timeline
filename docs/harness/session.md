# 새 채팅의 작업 절차

## 시작과 범위

루트 [AGENTS.md](../../AGENTS.md)를 따라 작업 트리와 최신 main을 확인하고
`node scripts/harness/run.mjs context`의 read 목록을 읽는다.
이 명령은 상태·승인을 바꾸지 않는다. 과거 채팅의 기억 대신 저장소의 문서·코드·결과를 사용한다.

- **열린 단계 작업:** 요청한 티켓과 선행 인수인계를 읽고 의존 관계를 확인한다.
  [트래커 규칙](../agents/issue-tracker.md)에 따라 claim·상태를 갱신한다. 중단된 작업은 기존 claim과 차단 이유를 확인한다.
- **완료된 MVP의 후속 작업:** `selected: null`, `frontier: []`는 현재 지도에 남은 단계가 없다는 뜻이다.
  [최종 인수인계](../wayfinder/handoffs/07-windows-release.md)와 [사용자 인수 범위](../release/user-acceptance.md)를 읽고
  새 요청의 대상·재현·완료 기준을 정한다. 완료 단계를 다시 열거나 새 단계가 승인됐다고 추정하지 않는다.
- **명시적 단계 조회:** context 뒤에 열린 티켓 ID를 전달한다. 완료·차단·미존재 단계는 오류를 반환하므로
  과거 설계를 찾을 때는 [문서 기준](../agents/domain.md)의 링크를 사용한다.

## 수행과 기록

기존 승인 사항은 재질문하지 않는다. 새 제품 결정이 필요할 때만 해당 결정을 논의하고,
문서 보정·버그 수정·제품 확장을 구분한다. 설계만 요청받은 작업에서 구현을 시작하지 않는다.

현재 동작은 코드와 실행 결과, 의도는 승인 문서, 제안은 근거와 미승인 표시로 기록한다.
결정 이유를 확인할 수 없으면 추정하지 않는다. 상세는 기존 담당 문서에 한 번만 쓰고 연결한다.
단계 실행은 [인수인계 양식](../wayfinder/handoffs/TEMPLATE.md), 문서·하네스 점검은
[재점검 기록](review.md)을 활용한다. 모든 후속 작업마다 새 인수인계나 ADR을 만들 필요는 없다.

## 종료

1. [변경별 검증](validation.md)을 실행하고 실패·미실행·환경 제한을 구분한다.
2. 관련 문서에 변경 이유·근거·실행 SHA/dirty·남은 항목을 기록한다.
   사용자가 후속으로 분리한 상세 검증을 이번 MVP 인수의 차단 조건으로 되돌리지 않는다.
3. 단계 작업일 때만 티켓·STATUS·MAP·인수인계를 함께 갱신한다.
   미완료 단계는 진행 중 상태와 차단 이유를 유지한다. 일반 후속 작업은 기존 완료 지도를 유지한다.
4. 승인된 작업 범위만 검증 후 main에 직접 커밋·push하고 원격 반영과 CI 상태를 확인한다.
   미완료 CI를 통과로 보고하지 않는다. PR·강제 push를 기본 절차로 사용하지 않는다.
5. 종료 메시지에 변경·검증·미검증·최종 SHA와 다음 작업의 문서 경로를 남긴다.

로컬 latest 보고서는 다음 실행에서 덮어쓴다. 전달할 실행 결과는 SHA와 CI URL을 함께 남긴다.
CI artifact의 경로·보관 기간은 [검증 안내](validation.md)를 따른다.
