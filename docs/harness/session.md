# 새 채팅의 작업 절차

## 시작

1. 사용자가 요청한 저장소·스테이지를 확인하고 최신 커밋과 로컬 변경을 확인한다.
2. 루트 AGENTS.md를 읽고 `node scripts/harness/run.mjs context`를 실행한다.
   출력의 read 목록을 읽는다. 특정 단계 요청은 `context 02-architecture`처럼 지정한다.
3. STATUS → 해당 티켓 → 직전 인수인계 → 필요한 설계 순서로 읽는다.
4. 요청받은 단계가 열려 있고 모든 선행 단계가 닫혔는지 확인한다.
   단계가 명시되지 않았으면 STATUS와 착수 가능한 단계를 근거로 다음 작업을 제시한다.
5. 착수하면 티켓의 assignee·status와 STATUS 표를 함께 갱신한다. 오래된 claim이면 직전 인수인계를 확인하고 재개 이유를 기록한다.

검사 성공은 설계 승인이나 제품 테스트 성공을 뜻하지 않는다.
중간 단계 재개는 새 단계 착수와 구분하며 사용자 확인 대기를 임의 해제하지 않는다.

## 수행

- 결정은 사용자와 논의하고, 이미 확정된 내용은 반복 질문하지 않는다.
- 설계 → 승인 → 구현 계획 → 요청된 구현 순서를 지킨다.
- 한 번에 작고 검증 가능한 변경을 한다. 버그는 재현 조건과 근거부터 확인한다.
- 필요한 공식 자료·스킬을 사용하고 중요한 결과는 저장소에 기록한다.
- 실패를 반복하면 프롬프트만 늘리지 말고 누락된 문서·도구·검증 경로를 보완한다.

## 종료

1. `node scripts/harness/run.mjs verify`와 변경에 맞는 앱 검사를 실행한다.
   아직 없는 앱 명령을 실행했다고 보고하지 않는다. 실패 보고서에서 문제를 확인하고 수정한다.
2. 인수인계 양식으로 실제 산출물·검증·승인·미결정·다음 작업을 기록한다.
3. 완료 기준을 충족했을 때만 티켓을 closed로 바꾸고 STATUS·지도도 갱신한다.
4. 완료하지 못했으면 in_progress 상태와 차단 이유, 재개 문구를 남긴다.
5. 검증 후 커밋하고 원격 반영 범위가 승인되어 있다면 push 결과를 확인한다.
   CI 실행 URL과 커밋을 인수인계 또는 종료 메시지에 남긴다. 로컬 보고서는 다음 실행 시 덮어쓰므로
   전달해야 할 로그는 별도 첨부하고, CI artifact는 14일 보관 기간을 고려한다.
6. 최종 메시지에 결과·검증·커밋·다음 채팅 문구를 간단히 전달한다.

## 시작 문구

```text
https://github.com/kdydesign/simple-timeline
이 저장소의 AGENTS.md를 따라 현재 상태를 확인하고 스테이지 1을 진행해줘.
Superpowers와 Wayfinder를 사용하고 이번 단계만 마친 뒤 인수인계를 남겨줘.
```
