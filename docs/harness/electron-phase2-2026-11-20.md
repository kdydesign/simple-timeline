# Electron 2차 분석 — 메인 이벤트 루프와 보조 창

일정 1만 건의 전체 스냅샷 조회는 메인 프로세스의 다른 작업을 지연시킬 수 있다. 도움말 사전 준비는 약 70ms의 첫 열기 이점과 상주 메모리 비용이 모두 관찰됐다. 두 결과는 서로 다른 실험에서 나왔다. [1차 실행 분석](electron-runtime-performance-2026-11-20.md) · [측정 스크립트·원시값·요약 ZIP](evidence/electron-phase2-evidence.zip)

## 메인 프로세스의 응답성

각 조건에서 renderer가 실제 preload API로 20회 읽기를 수행했다. 호출 간격 목표는 120ms이며 직전 호출이 끝난 뒤 다음 호출을 시작했다. 같은 구간에 메인에서 5ms 타이머를 걸어 콜백 사이의 실제 간격을 측정했다. 같은 프로필에서 작은 응답인 상태 조회를 대조군으로 사용했다. 각 fixture마다 새 프로세스 3회, API 실행 순서를 교대했다. 아래 값은 **실행별 중앙값 또는 최댓값의 범위**다.

| 일정 수 · API | IPC 왕복 중앙값 | 메인 타이머 간격 p95 | 메인 타이머의 최대 간격 | 50ms 초과 간격 / 실행 |
| --- | ---: | ---: | ---: | ---: |
| 3건 · 상태 조회 | 0.5–0.6ms | 5.3–5.8ms | 19.3–31.2ms | 0 |
| 3건 · 전체 일정 조회 | 1.1ms | 5.2–5.3ms | 7.2–34.4ms | 0 |
| 1만 건 · 상태 조회 | 0.5–0.6ms | 5.4–5.5ms | 10.4–31.0ms | 0 |
| 1만 건 · 전체 일정 조회 | 58.6–61.9ms | 27.1–28.0ms | 111.7–201.9ms | 2–3 |

IPC 핸들러는 메인에서 동기 SQLite 트랜잭션으로 전체 일정을 읽고 DTO를 만든다. 공유 저장소는 결과를 결합하고 다시 정렬한다. 1차 프로파일에서도 같은 경로가 확인됐다. 같은 프로세스가 처리하는 창 명령·트레이·알림도 이 구간의 영향을 받을 수 있다. 타이머 관측에는 스케줄링과 IPC 비용도 포함된다. 201.9ms 전체를 SQL 시간으로 귀속하거나, 반복 20회를 실제 사용자 발생 빈도로 해석할 근거는 없다. ## 도움말을 미리 준비하는 효과와 비용

3건 fixture에서 Home이 준비된 직후 바로 도움말을 여는 경우와, 백그라운드에서 창이 준비된 뒤 처음 여는 경우를 각각 새 프로세스 5회로 비교했다. 각 프로세스에서 도움말을 3번 더 닫고 열었다. 시작점은 메인이 사용자 열기 요청을 받은 마크다. 콘텐츠 준비는 renderer에서 읽기 상태를 적용하고 두 번의 애니메이션 프레임을 거쳐 메인에 알린 시점이다. 실제 모니터 표출·키보드 응답은 별도 지표다.

| 도움말 상태 | 창 표시 중앙값 | 콘텐츠 준비 중앙값 (범위) |
| --- | ---: | ---: |
| 사전 준비 전 첫 열기 | 88ms | 140ms (125–212) |
| 사전 준비 후 첫 열기 | 4ms | 70ms (43–72) |
| 닫았던 창 재열기 | 1.5ms | 31ms (23–37) |

재열기 값은 각 프로세스의 재열기 중앙값 10개를 집계했다. 별도 5회에서는 도움말을 한 번도 열지 않은 채 사전 준비 전후를 관찰했다. 준비된 도움말 renderer의 PSS 중앙값은 **51.3MiB**, CDP의 사용 중인 JS 힙은 **2.6MiB**였다. 같은 실행에서 메인·renderer·GPU·유틸리티 프로세스의 PSS 합계는 중앙값 **45.4MiB 증가**했다. PSS는 공유 페이지를 나눠 계산하며 준비 전후에 다른 프로세스의 메모리도 달라질 수 있다. 이 관찰값을 창 정책 변경 시 회수할 메모리로 보장할 수는 없다. ## 릴리즈노트를 본 뒤 트레이에 남는 메모리

10개 프로세스에서 먼저 도움말을 닫고, 릴리즈노트를 열고 닫는 동작을 3회 반복한 뒤 주 창도 트레이로 숨겼다. 보조 창은 닫기 후 숨김 상태로 남아 재열기에 쓰인다. 창별 OS PID를 직접 매핑했다.

| 같은 실행에서 관찰한 시점 | 앱 프로세스 PSS 합계 중앙값 |
| --- | ---: |
| 도움말만 열었다가 닫은 직후 | 284.2MiB |
| 릴리즈노트도 열고 처음 닫은 직후 | 316.1MiB |
| 릴리즈노트 세 번째 닫기 직후 | 316.6MiB |
| 주 창까지 트레이로 숨긴 직후 | 317.2MiB |

릴리즈노트 첫 열기·닫기에 따른 **실행별 증가분 중앙값은 31.5MiB**였다. 반복 중 세 renderer의 PID는 유지됐고 트레이에서는 세 창의 숨김을 확인했다. 짧은 반복에서 창이 계속 쌓이는 증거는 없었다. 장기 누수 판정에는 장시간 유지·GC·메모리 압박 후의 별도 측정이 필요하다. [릴리즈노트 창](../../src/main/release-window.ts)

## 다음 성능 실험의 우선순위

1. **실제 저장 한 번에서 메인 지연을 확인한다.** 1만 건 프로필에서 저장 완료와 재조회, 메인의 DB·DTO·공유 결합·정렬, renderer 반영을 같은 시간축에 기록한다. 별도로 창 조작 지연을 측정한다. 단일 변경도 같은 지연을 유발하는지 확인한 후 메인 작업을 줄일 구간을 고른다. 권한 회수와 실패 복구는 필수 검증 항목이다.
2. **창 정책은 비용과 사용 빈도를 같이 판단한다.** 1차 보고서에서는 도움말 프로세스의 존재가 드러났고, 이번에는 최초 열기 이점과 열지 않아도 드는 비용을 수치화했다. Windows 설치본에서 사전 준비 유무를 같은 기기·배율·프로필로 대조한다. 릴리즈노트의 사용 빈도가 낮다면 닫을 때 창을 해제하는 정책을 별도 실험하고, 재열기 지연·읽기 위치·트레이 복원을 함께 확인한다.
3. 1차의 [간트·달력 인덱스 공유 설계](../superpowers/specs/2026-11-20-home-planrail-performance-design.md)는 renderer 측 실험이다. 이 실험과 메인·보조 창 변경을 분리해야 어느 변경에서 효과가 났는지 알 수 있다. 1차 구현은 보류 상태다.

## 측정 환경과 재현

기준 소스 `23c5747`, 테스트 빌드의 Electron 45.2.1, Node 24.22.1, Linux x64, Xvfb 1440×1000, CPU 4코어·메모리 32GiB 할당. Chromium sandbox와 창별 preload 경계를 유지했다. 매번 일회성 프로필을 만들고 종료 후 삭제했다. 1만 건은 9,998건이 같은 날짜인 기존 스트레스 fixture다. Playwright로 제어했으며 메모리는 Linux의 `/proc/PID/smaps_rollup`, JS 힙은 CDP로 읽었다. Windows 설치본·사내 GPU·백신·실제 LAN의 지연은 미측정이다.

저장소 루트에서 `npm run build:test`를 실행한다. ZIP을 별도 폴더에 풀고 `DISPLAY`와 설치 환경의 `CHROME_DEVEL_SANDBOX`를 설정한 뒤, 같은 루트에서 `node "$PROBE_DIR/measure.cjs"`, `node "$PROBE_DIR/measure.cjs" --prewarm`, `python "$PROBE_DIR/summarize.py"` 순으로 실행한다. 결과는 스크립트 옆에 기록된다.
