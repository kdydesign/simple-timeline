# WorkRail의 Electron 시작과 트레이 상주 성능

일정 3건과 10,000건으로 Home을 열었을 때 창이 표시된 시간의 중앙값은 **246ms와 254ms**, 일정 데이터를 사용할 수 있게 된 시간의 중앙값은 **472ms와 619ms**였다. 일정이 많을 때 먼저 조사할 곳은 첫 스냅샷을 준비하고 Home에 반영하는 경로다. 이때 숨겨진 PlanRail 간트와 달력도 일정을 인덱싱한다.

## 조건과 근거

- [기존 기준선](performance-baseline-2026-11-20.md)의 소스는 `200e0ca`이며 조작 중의 스크롤·드래그·IPC가 중심이다. 이번 측정은 PostRail을 포함하는 깨끗한 `f317c14`의 Electron 테스트 진입점과 제품 renderer 빌드를 사용했다. 서로 다른 시나리오와 소스에서 나온 결과이므로 버전 간 회귀율을 계산하지 않았다.
- Linux x64 6.18.57, cgroup CPU 4코어, 메모리 32 GiB, Xvfb 1440×1000, UTC, Electron 45.2.1, sandbox 활성. 로컬 SQLite에 미리 3건 또는 10,000건을 넣고 건수를 확인했다. 같은 fixture의 일회성 프로필을 재사용해 차례를 번갈아 가며 각 5회 새 프로세스를 실행했다. fixture 삽입, DevTools 연결, CPU 프로파일러는 시간 측정에서 제외했다. OS 파일 캐시는 비우지 않았다. 10,000건 중 9,998건이 같은 날짜인 스트레스 자료다.
- 병목 분석은 별도 실행에서 했다. fixture별로 메인 V8 CPU 프로파일 1회, 프로세스별 Chromium 시작 트레이스 1회를 수집했다. 샘플 간격을 가중해 자기 시간과 호출 스택 포함 시간을 구분하고, renderer는 `index.html`의 navigationStart 뒤 500ms를 잘라 분석했다. GC, idle, 계측기 자체는 제품 함수 비용에서 제외했다. CPU 샘플은 추정치이고, 같은 스레드에서 겹치는 트레이스 이벤트의 시간을 더하면 중복된다.

## 창 표시와 Home 준비

단위는 ms이며 각 칸은 **중앙값 (최소–최대)**이다. 첫 두 행의 시작점은 메인 Node 프로세스 시계다. FCP는 renderer 탐색 시작이 기준이다. 각 구간의 중앙값은 개별 실행에서 차이를 계산한 후 구했다.

| 관측 지표 | 3건 | 10,000건 |
| --- | ---: | ---: |
| 창 표시 마크 | 246 (230–452) | 254 (221–271) |
| Home 일정 데이터 준비 마크 | 472 (457–681) | 619 (585–834) |
| app-ready → storage-ready | 12 (10–23) | 15 (14–18) |
| renderer-loaded → 첫 스냅샷 핸들러 반환 직전 | 100 (89–173) | 131 (120–332) |
| 스냅샷 핸들러 반환 직전 → Home 준비 마크 | 46 (38–54) | 145 (133–149) |
| renderer 탐색 → 첫 콘텐츠 표시(FCP) | 224 (204–320) | 236 (232–452) |

표의 마지막 스냅샷 구간에는 IPC 전달, renderer 상태 갱신·커밋, 준비 여부 관찰이 함께 들어간다. 준비 마크는 `timelinePhase`를 20ms 주기로 확인해 남긴다. 모든 메뉴가 입력 가능한 시점이나 모니터에 실제 프레임이 표시된 시점은 별도 측정이 필요하다. [마크 정의](../../src/main/bootstrap.ts#L273) · [렌더러 시계](../../src/main/startup.ts)

## 트레이에 숨긴 뒤

Home이 열린 뒤 창을 트레이로 숨기고, 주 창과 미리 준비한 도움말 창의 비표시 상태를 확인했다. 시작 트레이스에는 도움말 renderer가 주 창의 탐색 시작 약 1.29초/1.65초 뒤에 별도 프로세스로 생성됐다. 앱은 Home 준비 확인 약 1초 뒤 도움말을 준비한다. 따라서 첫 Home 준비 시간과 준비 후 상주 비용을 구분할 수 있다. [도움말 준비 시점](../../src/main/bootstrap.ts#L289)

30초 타이머를 포함하는 약 7.5초 구간에서 메인 V8의 idle 표본은 각 98% 이상이었다. 알림 평가의 포함 시간은 3건 7.9ms, 1만 건 22.7ms였다. 대량 fixture에서는 이 중 약 17.3ms가 스냅샷 조회 하위 호출에 있었다. 지속적인 JS 연산보다 주기적으로 깨워 전체 일정을 읽는 형태다. 이 비율은 OS가 측정한 앱 전체 CPU 사용률과 다르다. [알림 평가와 타이머](../../src/main/bootstrap.ts#L307) · [알림 엔진](../../src/main/reminders/engine.ts)

별도 실행에서 프로파일러를 끄고 약 29.6초간 Linux 프로세스별 사용자·커널 CPU tick의 차이와 마지막 PSS를 읽었다. Electron이 보고한 메인·GPU·유틸리티·renderer 2개의 합이다. PSS는 공유 페이지를 비례 배분한 상주 메모리다.

| 트레이 상태, 각 1회 | 전체 CPU 시간 | 한 코어 기준 평균 점유율 | PSS 합계 |
| --- | ---: | ---: | ---: |
| 3건 | 660ms | 2.2% | 약 254MiB |
| 10,000건 | 300ms | 1.0% | 약 285MiB |

이 한 구간에서는 일정 수에 비례하는 평균 CPU 경향이 없었다. 메모리는 특정 시점의 크기다. 기준 보고서의 GC 후 JS 힙, DOM·리스너 반복 측정은 별도의 지표이며 양쪽 모두 장기 누수를 확정할 근거가 없다.

## 개선 실험 순서

1. **Home에서 PlanRail을 처음 여는 비용을 분리한다.** 간트·달력을 최초 진입 때 준비하는 안과 스냅샷 인덱스를 한 번만 만들어 전달하는 안을 각각 측정한다. Home 준비 시간과 첫 PlanRail 클릭→조작 가능 시간 모두를 본다. 첫 진입 이후 스크롤·입력·날짜 복원이 유지돼야 한다. 기존 보고서에서 대량 가로 스크롤은 속성 변경 8,058회, 세로는 181회이므로 조작 성능은 별도 지표로 추적한다.
2. **대량 스냅샷의 단계를 계측한다.** 메인의 SQLite 조회·DTO 변환·공유 정렬, IPC 왕복, renderer 인덱싱·React 커밋을 같은 실행의 마크로 연결한다. 달력과 간트 인덱스 공유부터 검증하고, 전체 조회 변경은 권한 회수·삭제·저장 결과 불명 시 일관성까지 확인한다.
3. **트레이와 모듈 로드는 Windows 설치본으로 재확인한다.** 실사용 분포의 복제 데이터와 150% 배율에서 새 프로세스 시작·첫 메뉴 전환·최초 도움말을 측정한다. 트레이 상주는 여러 타이머 주기에 걸쳐 CPU와 메모리를 측정한다. 알림 평가의 조회 범위를 줄인다면 절전 복귀·누락 알림 회복을 함께 검사한다.

이번 측정에 실제 사내 LAN, SSH 연결, Node 설치, 대용량 PostRail 응답, Windows GPU·백신은 포함되지 않았다. 현재 시작 시간이 PostRail 추가 때문에 얼마나 변했는지는 같은 계측기로 두 커밋을 비교해야 알 수 있다. 제품 동작이나 배포 설정은 변경하지 않았다.

## 재현

소스 `f317c14`에서 `npm run build:test`로 테스트 진입점을 만들고 Xvfb와 Chromium sandbox를 준비한다. 함께 전달한 증거 압축의 스크립트 디렉터리에서 `WORKRAIL_ROOT`와 `DISPLAY`를 해당 환경에 맞춰 설정하고 아래 명령을 순서대로 실행한다. Linux CPU tick 및 PSS 측정에는 `/proc`와 Python 3의 sqlite3 모듈이 필요하다. 재측정은 기존 출력과 분리한 새 디렉터리에서 한다.

```sh
python capture.py
python capture.py main
python capture.py tray
python capture.py idle
python summarize.py
```

`startup.json`은 계측기 없는 10회 측정이다. `*-trace.json`은 Chromium 트레이스이고 `*-main.cpuprofile`과 `*-tray.cpuprofile`은 메인 V8 표본이다. `*-idle.json`에는 V8 프로파일러 없이 측정한 OS 카운터가 있다. 전체 앱 기능 검증 및 성능 개선 전후 비교는 이 분석의 실행 범위 밖이다.
